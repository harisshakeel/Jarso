# Mobile app (`apps/mobile`, `@jarso/mobile`)

Expo app for children and their parents. Wave 1: PIN sign-in, both jars, log a purchase and undo it, put in, take out, ask for extra, requests, history, settings. Wave 2 (parity with the web child app): goals, diary (got money, fix, versions, where it went), Learn, Jarso, News with live notices, and the offline outbox. Wave 3: the phone type scale, and parents on the phone. Parents sign in with email and password on the same screen ("I'm a child" / "I'm a parent") and get the web parent app's screens: Family (Needs you, Jarso's summary, children, the next two weeks), Children, Jarso, Inbox, each child's hub (jars, requests, due items, allowance, gifts, history, learning, rules, Jarso chats), cash handover, setup, settings, add a child and accept an invitation. Accounts are still created on the web; card payments and push come in later plans. Specs: `docs/superpowers/specs/2026-11-02-mobile-app-design.md`, `2026-11-03-mobile-wave-2-design.md`, `2026-11-03-mobile-wave-3-design.md`. Decisions: ADR 0016, 0017 (and 0015).

## Stack

- Expo SDK 58, React 19.3 and React Native 0.88, Expo Router (file routes in `app/`, only routing and composing).
- NativeWind v4 on Tailwind 3 (v5 is still a release candidate). The theme is built from `@jarso/brand/tokens` in `tailwind.config.js`; a parity test in `packages/brand` keeps `tokens.ts` equal to `tokens.css`. The theme's type scale is `mobileFontSize` (the phone scale, wave 3 spec §9), not the web `fontSize`.
- TanStack Query for server state. Hooks live in `src/features/<name>` and call `@jarso/data` with the app's Supabase client. Mutations invalidate the affected keys (`home`, `history`, `requests`; for parents `family`, `child`, `familyRequests`, `setup`).
- Pure logic, schemas and every line of child and parent copy come from `@jarso/core` (parent copy in each module's `parent-copy.ts` and `allowance/copy.ts`, moved word for word from the web components). The app never re-words it.
- react-native-reusables primitives in `src/components/ui` (barrel).

## Rules that are easy to break

- **`react-native-css-interop` is a direct dependency, pinned to the version NativeWind pins (0.2.7).** NativeWind's Babel preset rewrites JSX to `react-native-css-interop/jsx-runtime`. With pnpm's isolated linker the app cannot resolve a dependency of a dependency, so Metro fails. Declaring it in the app fixes this without `node-linker=hoisted`. When you bump NativeWind, bump this to the same version.
- **Entry is `index.ts`, not `expo-router/entry`.** It imports `@/lib/intl` first. Hermes lacks full `Intl` (PluralRules, RelativeTimeFormat, Locale, NumberFormat), and some core modules (`allowance/describe`, `family/sent-ago`) build formatters at import time, so the polyfills must exist before any route module is evaluated.
- **Env is read only in `src/config/env.ts`.** Three public vars, Zod-checked: `EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `EXPO_PUBLIC_API_URL`. `EXPO_PUBLIC_API_URL` must be `https:` except in dev builds (`__DEV__`), because it carries the bearer token. Anything `EXPO_PUBLIC_*` ships in the bundle, so no secret goes here. Copy `apps/mobile/.env.example` to `apps/mobile/.env.local` (not committed).
- **Data access.** Reads and writes go straight to Supabase with the signed-in user's session, so RLS applies; every mutation is an existing Postgres function that checks `auth.uid()` (and `is_parent_of` for a parent's write on a child). `apiFetch` (`src/lib/api.ts`) is used for `/api/v1/auth/child-sign-in`, `/api/v1/notices/dispatch`, `/api/v1/guide/state`, `/api/v1/learning/start` and, for parents, the routes that need the service key or a server-only check: `/api/v1/children` (add, remove, reset PIN), `/api/v1/invitations` (look up, accept), `/api/v1/family/summary` and `/api/v1/guide/drafts/confirm` (`docs/api.md`). Purchases go through the outbox. After every parent write that can leave a notice (handover, not given, a request decision, a gift, a note, rules) the app calls `dispatchNotices()`. The phone is not trusted: no money rule lives only in TypeScript.
- **Session** is stored in `expo-secure-store`, chunked (`src/lib/supabase/storage.ts`). See `docs/auth.md`, Mobile sign-in.
- **Money** is integer minor units. Each request create carries an `idempotencyKey` made once per sheet opening (`expo-crypto` `randomUUID`).
- **History undo uses the phone clock.** Mobile History decides `canUndo` from the phone's time (the web uses the server's). A wrong phone clock can show or hide the Undo button wrongly; the server still refuses an undo after a day.
- **Outbox.** Purchases go through core's outbox (`src/lib/outbox`): AsyncStorage, one key per user (`jarso-outbox:<userId>`), an in-process try-lock, `expo-network` for offline, `POST {EXPO_PUBLIC_API_URL}/api/v1/outbox` with the session's bearer. `<OutboxSync>` (mounted in `app/(child)/_layout.tsx`) flushes on foreground, network regain, token refresh, every 30 s and at the next backoff. Queued items are plain JSON in AsyncStorage (not encrypted, unlike the SecureStore session) and stay on the phone after sign-out, per user; Me warns first.
- **Learning.** Missions start online only through `POST /api/v1/learning/start`. Answers are graded on the phone for instant feedback (a haptic on a right answer), then every step, practice answer, check-in and finish goes through the outbox (kinds `step`, `practice`, `checkIn`, `completeMission`); the server grades again. The phone never calls a learning RPC. Reopening a mission resumes after the server's step results plus the steps still queued on the phone (`withQueuedSteps`). A topic's question saves nothing.
- **Jarso.** Shown only while `/api/v1/guide/state` says the guide is on; any guide screen opened while it is off goes to Home. Reads use `@jarso/data/guide` (own chats only, `asked_by is null`). A turn streams from `POST /api/v1/guide/turns` with `sendGuideTurn`, the global `expo/fetch` and the bearer; 52 s timeout; a resend of the same question reuses its `clientMessageId`. "Help me" / "Why?" beside a step and "Ask about this" on a topic open the `guide-sheet` form sheet with the context as a Zod-checked route param.
- **News.** The inbox reads `@jarso/data/notifications` (20 a page, `before` cursor). `<NoticeListener>` (child layout) subscribes to Realtime on the web's channel and filter (`recipient_id=eq.<uid>`), toasts a new notice, refreshes the badge and what the notice touches, closes the channel in the background and rejoins (and refetches) in the foreground.
- **UI.** Child: bottom tab bar (Home, Diary, Learn, Jarso, News, as the web; Jarso only when `/api/v1/guide/state` says the guide is on), Requests, Me, Goal and a diary line as pushed pages, form sheets for actions. Parent: Family, Children, Jarso (only when the guide is configured), Inbox (unread badge), Settings from the header avatar on every tab, the child's pages pushed with the web's page titles, the handover as a sheet. Safe areas, pull to refresh, light haptics on success, every control labelled with a role and at least 44 pt (48 dp on parent screens).
- **Two route groups, one role each.** `app/(child)` and `app/(parent)` each guard on the session's `status`: a parent who lands in the child group (cold start, a link) goes to Family, a child who opens a parent route goes to the child Home, a signed-out user goes to sign-in with `next`. Both groups own `/` and `/jarso`, so every href into a group is group-qualified (`/(parent)/(tabs)`, `/(child)/(tabs)`, `homeFor(role)`), and `useNextPath` in the parent layout maps the shared paths to the parent's before passing them on. Notice taps go through `noticeTargetRoute(target, role)` / `useOpenNotice(role)` (`src/features/news`).
- **Parent setup gate (ADR 0008).** The database does not enforce a finished profile, so the app does. `app/(parent)/_layout.tsx` reads `useParentSetup()` (parent details and family membership) and sends every parent screen except `setup` and `settings` (so a parent can still sign out) to `/(parent)/setup`, which shows only the missing step. A gate that can't be read shows the unavailable notice, never a parent screen. The path the parent was opening (an invite link with its `?code=`) rides along as `next` through sign-in and setup.
- **Parent text size.** The `(parent)` layout wraps its stack in `<BodySizeProvider size="parent">`; parent body text is 15/21 through `useBodySizeClass()`, a child's never under 16.
- **Payment slots.** `src/features/payments` holds `CardPaymentSlot`, `AutoChargeSlot` and `SavedCardsSlot`, placed in the handover, allowance and settings screens. They draw nothing until card payments land (plan 4).
- **Push.** `<PushBridge>` (root layout, inside `SessionProvider`, `src/features/push`) registers the phone once a child or parent is signed in: it creates the `notices` Android channel first (Android 13 prompts only once a channel exists), then, if permission is still undetermined, shows core's one-line reason (`pushPromptCopy`) and Android's prompt, once per user on the phone (AsyncStorage `jarso-push-asked:<userId>`). It posts the Expo push token to `POST /api/v1/push/tokens` (again when the token rotates) and keeps it as `jarso-push-token:<userId>` for the settings page. A `registerBeforeSignOut` hook sends `DELETE /api/v1/push/tokens` before the session goes; if that fails (offline) it calls `unregisterForNotificationsAsync()`, so the server's next send gets `DeviceNotRegistered` and deletes the row. A tap (`usePushTaps`, via `useLastNotificationResponse`, so a tap that launched the app counts) waits for the session, handles each push once, parses the payload with core's `pushDataSchema`, marks the notice read and opens `noticeTargetRoute(target, role)`; an overnight summary opens News and marks nothing; a push for another account (signed in on this phone before) or an unreadable one opens the role's Home. While the app is open, the user's own push goes to the shade without a banner (the in-app toast shows it) and anyone else's is not shown. Settings (parent) and Me (child) open a Notifications page per phone (`/(parent)/notifications`, `/(child)/notifications`): "Pause all" and four group switches saved on this phone's `device_push_tokens` row through `set_device_push_prefs` (optimistic, rolled back on error); the inbox and News still get every notice; a child sees the fixed quiet hours line; Android notifications off shows "Open phone settings"; an unregistered phone shows "Turn on". Web push keeps its own toggle. Nothing ever logs a token. Push needs the development build (not Expo Go) and only works on a real device.
- `console.log` is banned here too; use `@/lib` `logger`. It never logs tokens, PINs or child ids with amounts.

## Run it

```bash
pnpm mobile                    # expo start --dev-client (apps/mobile)
pnpm --filter @jarso/mobile android
pnpm --filter @jarso/mobile test   # jest-expo
```

The web app must be reachable from the phone for sign-in and push. Run `pnpm dev` on the laptop and set `EXPO_PUBLIC_API_URL` to `http://<laptop LAN IP>:3000` (phone on the same Wi-Fi), or to a tunnel URL (`localhost` points at the phone itself). Point the Supabase vars at the hosted project; there is no local Docker stack here.

**Expo Go no longer runs the app** (wave 3 adds native modules: `expo-notifications`, and the payment sheets). Build a development build once and install the APK on the phone:

```bash
(cd apps/mobile && eas build --profile development --platform android)   # or: (cd apps/mobile && npx expo run:android), local, needs the Android SDK
pnpm mobile                                                              # then open the dev build, not Expo Go
```

Rebuild only when a native module or config plugin changes (a new `expo-*` native package, `app.json` plugins or permissions); JS changes reload over Metro as before. The `development` EAS profile is an internal-distribution APK with `expo-dev-client`. Check bundling without a device with `(cd apps/mobile && npx expo export --platform android)`, then delete `apps/mobile/dist/`. Run every `eas` and `npx expo` command from `apps/mobile`, where `eas.json` and `app.config.ts` live.

**Push credentials (FCM).** Android push goes through Firebase Cloud Messaging; neither file below is ever in the repo (see `docs/security.md`).

1. Upload the FCM v1 service-account key to EAS: `(cd apps/mobile && eas credentials)` → Android → the app → Google Service Account → FCM V1. It lives only in EAS.
2. Store `google-services.json` as an EAS file env var, once per environment: `(cd apps/mobile && eas env:create --name GOOGLE_SERVICES_JSON --type file --visibility sensitive --environment development)` (repeat for `preview` and `production`). `app.config.ts` sets `android.googleServicesFile` from it. A local `google-services.json` is git-ignored; a build without the var still works, it just gets no push token.

## Layout

```
apps/mobile/
  index.ts                 # entry: Intl polyfills, then expo-router/entry
  app/                     # (auth)/sign-in; (child)/(tabs)/{index,diary,learn,jarso,news}, pages: requests, me, goal, entry/[entryId], learn/{[missionKey],practice,check-in,week,week-question,topics/[topicKey]}, jarso/[conversationId]; sheets: purchase, put-in, take-out, ask-extra, received, goal-sheet, guide-sheet
                           # (parent)/(tabs)/{index,children,jarso,inbox}, pages: settings, setup, invite, children/new, children/[childId]/{index,history,learning,rules,allowance,gifts/{new,[giftId]},guide/{index,[conversationId]}}; sheet: children/[childId]/handover/[kind]/[id]
  src/features/<name>/     # auth, jars, diary, goals, learning, guide, news, requests, history, settings, allowance, family, rules, setup, payments; home, learn and parent (composites)
  src/components/          # ui (primitives), sheet (shared sheet parts), screen
  src/lib/                 # supabase client + storage, api, outbox, query keys, errors, notices, logger, intl
  src/config/{env,site}.ts
  tests/                   # jest-expo
```

## Device e2e (Maestro)

Flows in `apps/mobile/e2e/`: `sign-in`, `money-loop` (purchase and undo, put in, take out, ask extra, cancel, got money), `diary` (fix, earlier versions), `goal`, `learn`, `news`, `guide`, `offline` (a purchase queued in airplane mode replays). Parent flows: `parent-sign-in` (a sub-flow the others start with), `parent-approve-request` (the child asks for extra, the parent approves it), `parent-cash-handover` (a due allowance handed over in cash), `parent-allowance` (change the amount, see it on the hub), `parent-add-child` (a random nickname). Parent flows take `-e PARENT_EMAIL=… -e PARENT_PASSWORD=…`; `parent-approve-request` also takes the child vars and `parent-allowance` takes `CHILD_NICKNAME`. The test parent must have finished setup, have the test child in their family and, for the handover flow, an allowance due. Install the development build (`(cd apps/mobile && eas build --profile development --platform android)`, or `(cd apps/mobile && npx expo run:android)`; see Run it), start `pnpm mobile`, then `maestro test -e CHILD_FAMILY_CODE=… -e CHILD_NICKNAME=… -e CHILD_PIN=… e2e` from `apps/mobile` (or `pnpm --filter @jarso/mobile e2e` with the same `-e` flags). The seeded child's first diary row must be fixable (a purchase or got-money line) and put-in and take-out must be allowed by the family's rules. `push` (tagged `push`; a physical Android phone with the development build and FCM credentials in EAS, never an emulator) signs the parent in, allows notifications, runs `scripts/child-asks.js` (the test child asks for extra over HTTP, then dispatches), opens the push from the shade onto the child's hub, signs out, and checks the next ask does not buzz the phone. It also takes `-e API_URL=… -e SUPABASE_URL=… -e SUPABASE_PUBLISHABLE_KEY=…` with the parent and child vars; run the other flows without it with `--exclude-tags push`. Credentials are the hosted test family's, passed from the shell and never committed. Not run in CI.

Unverified until run on a device: `expo/fetch` NDJSON streaming and abort on Android, Realtime `setAuth` with the SecureStore session, the outbox draining on reconnect, and Hermes `Intl` parity for `familyToday`. The checklist is in `tasks/todo.md`.

Cross-module imports go through each module's `index.ts`, as on the web.
