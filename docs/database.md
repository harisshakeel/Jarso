# Database (Supabase)

Postgres via Supabase. Schema is managed **only** through SQL migrations in `supabase/migrations/`. Never edit the schema from the dashboard in a shared environment.

## Local workflow

```bash
pnpm db:start                 # start local Supabase (Docker required); prints URL + keys
pnpm exec supabase status     # show keys again → copy into apps/web/.env.local (start from the root `.env.example`)
pnpm db:migration add_thing   # create supabase/migrations/<ts>_add_thing.sql
pnpm db:reset                 # rebuild local DB from migrations + seed.sql
pnpm db:types                 # regenerate packages/db/src/database.types.ts from local DB
pnpm db:types:linked          # regenerate types from linked hosted project
pnpm db:stop
```

Studio: http://127.0.0.1:54323 · Inbucket (auth emails): http://127.0.0.1:54324

## Deploying migrations

```bash
pnpm exec supabase link --project-ref <ref>
pnpm db:push                  # always --linked (explicit; CLI default is changing)
```

Normally you don't run this. Supabase's GitHub integration watches `main` (Supabase → Project Settings → Integrations → GitHub, working directory `.`, production branch `main`, "Deploy to production" on, preview branches off) and applies new migrations to the hosted project on every merge. Only `main` deploys; PRs never touch a hosted database. Status and logs are in the Supabase dashboard. The commands above are the fallback if the integration is off or a deploy fails.

Because `supabase/config.toml` has a `[remotes.production]` block naming the project, the integration also syncs the `[auth]`, `[api]`, `[db]` and `[storage]` settings from that block on each deploy, so auth settings are code. Seeds are never applied to production.

Each migration file runs in one transaction (so no `create index concurrently`), and a migration older than the latest applied one still runs, with a warning. Migrations must be forward-only and expand/contract, because the integration and the Vercel build run side by side; to undo, write a new migration.

Emergency rollback of a migration already on hosted (prefer a fix-forward migration or merging the fix):

1. Run SQL that reverses it in the Supabase SQL editor (in one transaction).
2. `pnpm db:revert <version>` (e.g. `pnpm db:revert 20261101230000`) marks it as not applied in the hosted history, so the next `pnpm db:push` applies it again. It runs no SQL itself.

## Migration rules

1. One logical change per migration. Name it `snake_case` describing the change.
2. **Every table in `public` gets RLS enabled in the same migration that creates it.** No exceptions.
3. Write explicit policies per operation (`select`, `insert`, `update`, `delete`) and role (`to authenticated`). No catch-all `for all` policies unless genuinely identical.
4. Use `(select auth.uid())` (wrapped) in policies — it's evaluated once per query, not per row.
5. Index every foreign key and every column used in RLS predicates.
6. Standard columns: `id uuid primary key default gen_random_uuid()`, `created_at timestamptz not null default now()`, `updated_at timestamptz not null default now()` + `public.set_updated_at()` trigger.
7. Functions: `set search_path = ''` and fully-qualify names. `security definer` only when needed, and never exposing it to callers who could abuse it.
8. Comment non-obvious tables/columns (`comment on …`).
9. After any migration: `pnpm db:reset && pnpm db:types`, commit the regenerated types.
10. Destructive changes (drop/rename column) ship in two deploys: stop using it in code → then drop.

## Data access in code

```
service.ts  ──►  repository.ts  ──►  supabase client
```

- `repository.ts` is the **only** place that references table/column names. It maps rows → domain types (`snake_case` → `camelCase`).
- Use the **server client** (`@/lib/supabase/server`) by default — it runs as the user, so RLS applies.
- `@/lib/supabase/admin` bypasses RLS. Only for trusted backend jobs/webhooks, never with user-supplied filters, and always after an explicit authorization check.
- Check `error` on every Supabase call; wrap in `AppError` with `cause`.

RLS helpers (`stable security definer`, `search_path = ''`, executable by `authenticated` only): `is_approved_member(family_id)`, `is_parent_of(child_id)`, `is_self(child_id)`, `current_family_id()`. Reuse them in every family-scoped policy.

Functions:

- `create_family(currency, timezone) → uuid` — caller must be a `parent` with no membership; raises `JA401` / `JA403` / `JA409`, `22023` for an unknown timezone.
- `register_child(child_id, family_id, nickname, pin, consent, invitation_id default null)` — approved parent of the family adds a child-role profile with no membership. With `invitation_id`, locks the invitation `for update` and requires it `pending` and unexpired, then marks it `accepted` (`accepted_by`, `child_id`, `family_id`) in the same transaction. Clears `parent_email` on the accepted invitation. Overwrites any stale `child_credentials` row and clears the child's lock state. Raises `JA403` (not a parent of the family, or no consent), `22023` (PIN not 4–6 digits, nickname not 1–20 letters, digits, spaces or `_ . ' -`), `JA404` (invitation missing, used or expired), `JA409` (child unavailable or nickname taken). Audits `child.added` and, with an invitation, `invitation.accepted`.
- `set_child_pin(child_id, pin)` — `is_parent_of` caller; sets the PIN and clears every lock (all `child_pin_attempts` rows and the safety cap). Audits `child.pin_reset`. The service then calls `revoke_user_sessions`.
- `remove_child(child_id) → boolean` — approved parent of the child's family. Else inserts `pending`; if at least one `withdrawal_auto_approve` rule exists and all pass (approved + handed_over total + amount ≤ limit) it is `approved`, `auto true`, no notice; otherwise `notify_parents('withdrawal_requested', {amount_minor, reason})`. Returns `{status: pending|approved, request_id}`.
- `decide_withdrawal(request_id, approve, note) → text` — parent only (`JA403`, also for a missing request); decides a pending withdrawal or emergency (a deposit → `22023`). For an emergency Save is not checked and the child gets `emergency_decided`. Locks the request, then the ledger lock. Not `pending` → `already_decided`. Approve needs `amount <= balance(save) − reserved_save + amount`, else `over_available` (stays pending). Sets `decided_by/at`, note (trimmed, ≤140, else `22023`), `notify_child('withdrawal_decided', {amount_minor, approved})`. Returns `approved|rejected|already_decided|over_available`.
- `complete_request(request_id, idempotency_key) → text` — parent only (`JA403`); key not stored, blank or over 200 → `22023`. Hands over an approved withdrawal or emergency, or confirms a pending deposit. Locks the request, then the ledger lock. `handed_over` or `confirmed` → `already_completed`; otherwise only an `approved` withdrawal or a `pending` deposit proceeds (any other → `not_approved`) to `post_request`. Returns `completed|already_completed|not_approved|over_available`. Rules are not re-checked (a lowered cap does not block an approved hand-over).
- `create_emergency(child_id, amount_minor, reason, idempotency_key) → jsonb` — child only (`JA403`). The child asks for extra money (FR15): always `pending`, no cap or auto rule, nothing reserved. Amount outside 1..100000000000, missing or blank reason or one over 140, blank key or over 200 → `22023`; a key used by another kind → `JA409`. Takes the ledger advisory lock. A repeated (child, key) returns that request's current status and id. Notifies parents (`emergency_requested`).
- `create_deposit(child_id, amount_minor, idempotency_key) → jsonb` — child only (`JA403`). Amount outside 1..100000000000, blank key or one over 200 → `22023`. Takes the ledger advisory lock. A repeated `(child, key)` returns `{status: <current status>, request_id}` (`JA409` if that key is a withdrawal). `amount > available_spend` → `{status: over_available, available_minor}`. Else inserts `pending` (holds Spend via `held_spend`); if at least one `deposit_auto_confirm` rule exists and all pass (`request_window_total(deposit, {confirmed})` + amount ≤ limit; item: amount ≤ limit) it calls `post_request` in the same transaction and sets `confirmed`, `auto true`, no notice; otherwise `notify_parents('deposit_requested', {amount_minor})`. Returns `{status: pending|confirmed, request_id}`.
- `decide_deposit(request_id, note) → text` — parent only (`JA403`, also for a missing request); reject only ("Didn't get it"; confirming is `complete_request`). Not a deposit or note over 140 → `22023`. Locks the request, then the ledger lock. Not `pending` → `already_decided`. Sets `rejected`, `decided_by/at`, note (trimmed), posts nothing (the hold is released), `notify_child('deposit_decided', {amount_minor, approved: false})`. Returns `rejected|already_decided`.
- `post_request(request_id, actor) → text` — **internal, no grants**: the only path that posts a request to the ledger. Emergency: one `grant_in` to `spend` labelled with the reason, key `request:<id>:in`, sets `handed_over` (the grant lands in Spend, decided 2026-10-31). Withdrawal: re-checks `amount <= balance(save) − (reserved_save − amount)`, inserts `withdrawal_out` (save) and `withdrawal_in` (spend), `source_type request`, label = reason or `Taken out of Save`, keys `request:<id>:out|in`, sets `handed_over`, `completed_by/at`. Deposit: re-checks `amount <= balance(spend) − (held_spend − amount)`, inserts `deposit_out` (spend) and `deposit_in` (save), label `Put into Save`, same keys, sets `confirmed`, `completed_by/at` (an auto-confirm records the child as actor). Either refusal returns `over_available`; success `completed`; any other kind raises `22023`.
- `cancel_request(request_id) → text` — the child cancels their own `pending` request; a parent cancels a `pending` or `approved` withdrawal or emergency (parents decide deposits via `decide_deposit`: `22023`). Takes only the row lock (no ledger lock), posts nothing. Returns `cancelled|already_closed`; `JA403` otherwise.
- `withdrawal_cap_remaining(child_id) → bigint` — the smallest room left under the child's `withdrawal_cap` rules: each week or month cap minus `request_window_total(pending, approved, handed_over)` in its window, floored at 0; an item cap counts as unused; `null` when the child has no cap. `JA403` unless self or parent of. The child's take-out sheet uses it to show how much can be asked for.
- `save_goal(name, emoji, target_minor, plan_minor) → uuid` — child only. Creates or updates the caller's active goal. A plan over the allowance (any schedule not stopped) raises `22023 plan_over_allowance`; without a schedule a plan over the target raises `22023 plan_over_target`. `JA403`.
- `archive_goal(goal_id)` / `mark_goal_celebrated(goal_id)` — child only, own active goal; celebrating needs `reached_at` and happens once. `JA403`.
- `goal_progress(child_id) → (goal_id, counted_minor, reached)` — counted = `balance(save) − reserved_save`, never below 0; records `reached_at` the first time it covers the target. No row without an active goal. Self or parent; `JA403`.
- `record_purchase(child_id, amount_minor, label, idempotency_key, occurred_at default null, category default 'other') → jsonb` — child only (`is_self`, approved child membership, else `JA403`). Amount outside 1..100000000000, label (trimmed, empty → null) over 60, or a blank key or one over 200 characters → `22023`. Takes the child's ledger advisory lock (no source row). A repeated key (`purchase:<child>:<key>`) returns `{status: recorded, entry_id, notices: 0}` with the original entry, without re-checking Spend or limits. Otherwise `free = balance(spend) − held_spend`; refuses with `{status: not_enough_spend, free_minor}` (posting nothing) when overspend is off and `amount > free`, or when it is on, `held_spend > 0` and Spend would drop below `held_spend`. Inserts the `purchase` (`spend`, `out`, `source_type diary`, `created_by` caller, `occurred_at` = `resolve_occurred_at(occurred_at)`), then `evaluate_spend_limits`. A backdated purchase lands on its own diary day, spending-limit window and undo window; the Spend check uses the current balance. Returns `{status: recorded, entry_id, notices}`.
- `record_purchase_at(child_id, amount_minor, label, idempotency_key, now, category default 'other') → jsonb` — **internal, no grants**: the clock seam behind `record_purchase` (pgTAP, demo clock); the purchase's `occurred_at` and limit windows use `now`. A category that is not a spend key raises `22023`; null means `other`.
- `resolve_occurred_at(p) → timestamptz` — **internal, no grants**: when a child action happened (the outbox route derives it from the action's age on the server clock). Null or any future time → `now()`; more than 7 days back → `22023` (a backstop); otherwise `p`. Used by `record_purchase`, `record_practice_result` and `complete_mission`. `start_mission` stays online-only (it returns the attempt id); `record_step_result` and `complete_checkin` have no day logic and take no time.
- `send_handover_reminders(now default now()) → int` — **cron only, no grants**; `pg_cron` job `send-handover-reminders` at `7 * * * *` (same guard and `statement_timeout` command as `generate-due-occurrences`). For each allowance occurrence still `due`, with `d` = family today − `due_on`: `d = 0` notifies the parents and the child (`allowance_due`, window `<id>:due`); `d > 0 and d % 3 = 0` notifies the parents (`handover_reminder`, window `<id>:<family date>`). Source `allowance_occurrence`, payload `{amount_minor, due_on, days_overdue}`. Reruns add nothing; an occurrence first seen late waits for its next 3-day mark; paused schedules still remind; confirmed or closed occurrences never do. Returns rows inserted.
- `send_child_note(child_id, text, idempotency_key) → text` — parent of the child only (`JA403`); a short note for the child's News, written as a `parent_note` notice (`{text}`, source `note`, `source_id` the parent, `window_key` `note:<key>`). Text trimmed of every kind of whitespace, 1 to 140 characters, and a key of at most 200 (`22023`). After the parent, child and length checks, a repeat key returns `already_sent` before the daily cap; otherwise at most 20 notes per child per rolling day (`JA429`), under a per-child advisory lock. Audits `note.sent` with empty details: the text is never copied. Returns `sent|already_sent`.
- `mark_notifications_read(ids uuid[] default null) → int` — `authenticated`; sets `read_at` on the caller's own unread notices (the given ids, or all when null). The only write path: `notifications` has no update grant. Returns the count.
- `unread_notification_count() → int` — `authenticated`; the caller's unread notices in families they are an approved member of.
- `evaluate_spend_limits(entry_id) → int` — **internal, no grants**; called under the ledger lock. Per `spend_limit` rule of the child: `item` notifies when the amount is over the limit (window `spend_limit:item:<entry_id>`); `week`/`month` sum every live (not reversed) recorded Spend purchase from `rule_window_start` up to the next local window start (exclusive), this one included (`after`; `occurred_at` is the transaction start, so a purchase that waited on the ledger lock can carry an earlier time than one already committed: it still counts that one within its window, and never one from the next window), and notify when `after − amount <= limit < after` (window `spend_limit:<period>:<window start as a family-local date>`). `notify_parents` kind `limit_exceeded`, source `ledger_entry`, payload `{amount_minor, limit_minor, period, total_minor}`. Returns the number of rules whose notice it wrote, from the `notify_parents` row counts (a window already noticed is deduplicated and not counted). Undo never adds or retracts a notice.
- `undo_diary_entry(entry_id) → text` — the entry's child only, with an approved child membership in the entry's family (`JA403`, also for a missing entry); not a purchase or a diary `gift_in` → `22023`, and so is a line a fix already replaced. Locks the entry `for no key update`, then the ledger advisory lock. Returns `already_undone` if reversed, `too_late` if the chain root's `created_at < now() − 24 hours`, else inserts a `reversal` (flipped direction, same jar, mode, amount and category, `reverses_entry_id`, key `reversal:<entry_id>`) and returns `undone`. **The reversal keeps the line's `occurred_at`** (it used to take the undo time), so it lands on the line's own day. Undoing money received refuses with `not_enough_spend` (Spend would go short, by the `record_purchase` rule) or `not_enough_save` (`balance(save) − amount < reserved_save`). `undo_diary_entry_at(entry_id, now)` is its **internal, no grants** clock seam.
- `undo_purchase(entry_id) → text` — kept as a SQL alias of `undo_diary_entry_at(entry_id, now())`. `undo_purchase_at` was dropped.
- `record_money_received(child_id, amount_minor, jar, category, label, idempotency_key) → jsonb` — child only (`JA403`); input checks (amount range, label length, a received key, a spend or save jar, a key) run before the ledger lock, `22023` otherwise. Inserts a `gift_in` (`in`, `source_type diary`) at once, then `notify_parents` kind `money_received`, source `ledger_entry`, no window key (never deduplicated), payload `{amount_minor, category, jar}`. A repeated key returns the original entry and sends no second notice. Returns `{status: recorded, entry_id}`. `record_money_received_at(…, now)` is its **internal, no grants** seam.
- `correct_diary_entry(entry_id, amount_minor, category, label, idempotency_key) → jsonb` — child only. Locks the entry, then the ledger lock. Replay (key `fix:<child>:<key>`) returns `{fixed, entry_id}` first; then `not_fixable` unless the line is live, a diary `purchase` or `gift_in`, and its chain root's `created_at` is within 7 days; `unchanged` when amount, category and trimmed label all match (a legacy null category counts as `other`); a category not valid for the line's kind raises `22023`. Guards the amount the fix takes out (purchase: new − old, as `record_purchase`; `gift_in`: old − new, as undoing it) and returns `not_enough_spend` (with `free_minor`) or `not_enough_save`. Otherwise writes a reversal and a new line with the same kind, jar and `occurred_at`, `corrects_entry_id` set, runs `evaluate_spend_limits` for a purchase, and sends `entry_corrected` (payload `{kind, old_amount_minor, amount_minor}`) only when the amount changed. Returns `{status: fixed, entry_id}`. `correct_diary_entry_at(…, now)` is its **internal, no grants** seam.
- `list_entry_versions(entry_id) → table` — the entry's child or an approved parent (`JA403` otherwise, also for a missing entry); the whole chain from its root, oldest first.
- `diary_chain_root(entry_id) → ledger_entries` — **internal, no grants**: walks `corrects_entry_id` back to the first line. `evaluate_spend_limits` keys an item limit's notice on the root's id, so fixing a purchase never re-notifies.
- `hit_rate_limit(key, window, max) → boolean` — **service_role only**; counts a hit in the `date_bin(window, now(), epoch)` window and returns `true` while the count is within `max`.

- `progress_level(sparks) → smallint` and `progress_wear_level(wear) → smallint` — **immutable, internal**: level 1..10 for a Sparks total (thresholds 0, 100, 250, 450, 700, 1000, 1400, 1900, 2500, 3200) and the level an outfit needs (none and cap 1, shades 3, headphones 4, crown 5). They mirror `@jarso/core/progress` and `@jarso/core/mascot`; keep the two in step.
- `progress_lock(child_id) → child_progress` — **internal, no grants**: creates the child's row if missing (approved child members only) and locks it `for update`; null for anyone else. Always the last lock taken.
- `progress_award(child_id, kind, source_key, amount, now default now(), checkin default null) → int` — **internal, no grants**: the one award engine. Pays `amount` Sparks once per `(child, source_key)` on the family-local day of `now`, within the daily caps (log 3 a day, check-in 1, step 20, save 2); an over-cap or replayed award pays 0, but a replayed log or step still marks its day active. Values: log 10, check-in 5, step 15, save 20, goal milestone 25, goal reached 100. For `checkin` it also writes the answer to `child_activity_days` under the row lock (first answer of the day wins), so callers never write that table. Returns the Sparks paid. Updates the level, the stored streak and the counters, then `progress_check_badges`. `JA404` for a non-child, `22023` for a bad kind, amount, key or answer.
- `progress_check_goal(child_id, award) → void` — **internal, no grants**: records each 25/50/75/100% milestone of the active goal once (key `goal:<goal>:<pct>`, 25 Sparks, or 0 when `award` is false), and goal reached (key `goal_reached:<goal>`, 100, or 0 inside the 7-day cooldown: at most one paid per rolling 7 days). A milestone already passed is never paid later: a new goal, or a target change, records the passed ones at 0. `goals_reached_count` and the `goal_reached` badge move only when the reached award was real, so the badge means saving.
- `progress_streak(child_id, today) → (streak, rest_used_this_week)` — **internal, no grants**, `stable`: counts consecutive active family-local days; one rest day per ISO week (weeks start Monday) covers a single missed day when the day before was active. `get_progress` recomputes it live, so a streak the child let slide shows as it is today.
- `progress_check_badges(child_id, day) → …` — **internal, no grants**: grants every badge the counters, best streak, level, goal state and the logs of the 7 days ending `day` now justify. Never removes one.
- Award triggers (all `security definer`, **no execute grants**; each wraps its award in its own `exception when others` block and raises only a warning): `progress_on_ledger_entry` (after insert on `ledger_entries` when `mode = 'recorded'` and the kind is `purchase`, `gift_in` or `deposit_in`, or the jar is `save`) awards a log for a first diary `purchase` or diary `gift_in` (key `log:<entry>`, never a fix's new line, which has `corrects_entry_id`, nor a reversal) and a save for `deposit_in` (key `save:<request>`), then runs the goal check for any recorded Save row. `progress_on_step_result` (after insert on `step_results`) pays a step in the main phase (key `step:<mission>:<step>`, once for life, 20 a day) and in the replay phase only marks the day active (`progress_mark_active`, internal). `progress_on_mission_completed` (after update of `status` on `mission_attempts`, into `completed`) counts the mission only the first time the child completes that `mission_key` (a repeat completion adds nothing) and checks the mission badges, no Sparks. `progress_on_goal_insert` and `progress_on_goal_target` (after insert on `goals`, after `target_minor` changes) call `progress_on_goal_change`: milestones already passed are recorded at 0 and `goal_set` is granted. Practice money never reaches the engine: the ledger trigger fires only on `recorded` rows.
- `daily_checkin(answer) → jsonb` — child only; "anything about money today?" once a family-local day, `yes` or `nope`. The first answer of the day is kept and pays 5 Sparks (key `checkin:<day>`), a later one returns `already`. Returns `{status: recorded|already, sparks}`. See `docs/api.md`. `daily_checkin_at(answer, now)` is its **internal, no grants** clock seam (pgTAP).
- `set_jarso_look(lid, wear)` — child only; sets the lid colour and outfit. `get_progress(child_id) → jsonb` — the child or their parent; the single read model. Both in `docs/api.md`.

Lock order: ledger writers lock the source row first, then the child's ledger advisory lock; never the reverse. The source row lock (`lock_occurrence_for_parent`, `lock_gift_for_parent`, `for update`) comes first because the row says which child it belongs to; then `pg_advisory_xact_lock(hashtextextended('ledger:' || child_id, 0))`; then the ledger inserts. Every later writer (purchases, savings requests) follows the same order, so balance checks are serialised per child without deadlocks. The request functions follow it: `decide_withdrawal`, `complete_request` and `decide_deposit` lock the `requests` row first (`for update`), then the ledger advisory lock; `cancel_request` takes only the row lock, since it posts nothing; `create_withdrawal` and `create_deposit` have no row yet, so they take the ledger lock first and the `(child, key)` unique index settles a repeated key. `post_request` runs under both locks and is never called directly. Purchases and requests share the one ledger lock, so a purchase racing a deposit sees the hold. `apply_payment` puts the `payments` row lock in front (payment, then source row, then ledger lock); the gift and not-given guards lock the source row and only read `payments`, so they cannot deadlock with it. Future reversal writers (undo of any ledger entry) lock the entry row first (`for no key update`), then the ledger advisory lock, as `undo_diary_entry` and `correct_diary_entry` do.

Progress lock order (2026-11-06): the progress triggers fire inside the caller's transaction, after the caller holds its source locks, so `child_progress` is always the last lock: ledger advisory lock (and the `requests`, attempt or goal row before it) first, then `progress_lock` on `child_progress`. Nothing in the progress functions takes a source lock after the progress row, and `daily_checkin` goes only through `progress_award` (the check-in answer is written there, under the row lock), so there is no inversion with the money writers. **An award failure never blocks a money or lesson write**: every award trigger body runs in its own `begin … exception when others then raise warning` block, so a failed award rolls back to its own savepoint and the purchase, deposit, step or goal write commits anyway. The cost is that a failed award is skipped, not retried; the next award for that child works normally. Sparks stay out of the ledger by construction: no progress function inserts into `ledger_entries`, no function takes Sparks back (undo, a fix or a reversal changes nothing in `spark_events`), and the ledger trigger only fires on `recorded` rows.

All four progress tables have RLS on with explicit select, insert, update and delete policies and `insert, update, delete, truncate` revoked from `authenticated` (all revoked from `anon`): the child and their parents read `child_progress`, `spark_events` and `child_badges`; only the child reads `child_activity_days`. Every write goes through the functions above.
