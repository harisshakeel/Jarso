# Database (Supabase)

Postgres via Supabase. Schema is managed **only** through SQL migrations in `supabase/migrations/`. Never edit the schema from the dashboard in a shared environment.

## Local workflow

```bash
pnpm db:start                 # start local Supabase (Docker required); prints URL + keys
pnpm exec supabase status     # show keys again → copy into .env.local
pnpm db:migration add_thing   # create supabase/migrations/<ts>_add_thing.sql
pnpm db:reset                 # rebuild local DB from migrations + seed.sql
pnpm db:types                 # regenerate types from local DB
pnpm db:types:linked          # regenerate types from linked hosted project
pnpm db:stop
```

Studio: http://127.0.0.1:54323 · Inbucket (auth emails): http://127.0.0.1:54324

## Deploying migrations

```bash
pnpm exec supabase link --project-ref <ref>
pnpm db:push                  # always --linked (explicit; CLI default is changing)
```

Normally you don't run this. Supabase's GitHub integration watches `main` (Supabase → Project Settings → Integrations → GitHub, working directory `.`, production branch `main`, "Deploy to production" on, preview branches off) and applies new migrations to the hosted project on every merge. Only `main` deploys; PRs never touch a hosted database. Status and logs are in the Supabase dashboard. The commands above are the fallback if the integration is off or a deploy fails.

Because `supabase/config.toml` has a `[remotes.production]` block naming the project, the integration also syncs the `[auth]`, `[api]`, `[db]` and `[storage]` settings from that block on each deploy, so auth settings are code. Seeds are never applied to production.

Each migration file runs in one transaction (so no `create index concurrently`), and a migration older than the latest applied one still runs, with a warning. Migrations must be forward-only and expand/contract, because the integration and the Vercel build run side by side; to undo, write a new migration.

## Migration rules

1. One logical change per migration. Name it `snake_case` describing the change.
2. **Every table in `public` gets RLS enabled in the same migration that creates it.** No exceptions.
3. Write explicit policies per operation (`select`, `insert`, `update`, `delete`) and role (`to authenticated`). No catch-all `for all` policies unless genuinely identical.
4. Use `(select auth.uid())` (wrapped) in policies — it's evaluated once per query, not per row.
5. Index every foreign key and every column used in RLS predicates.
6. Standard columns: `id uuid primary key default gen_random_uuid()`, `created_at timestamptz not null default now()`, `updated_at timestamptz not null default now()` + `public.set_updated_at()` trigger.
7. Functions: `set search_path = ''` and fully-qualify names. `security definer` only when needed, and never exposing it to callers who could abuse it.
8. Comment non-obvious tables/columns (`comment on …`).
9. After any migration: `pnpm db:reset && pnpm db:types`, commit the regenerated types.
10. Destructive changes (drop/rename column) ship in two deploys: stop using it in code → then drop.

## Data access in code

```
service.ts  ──►  repository.ts  ──►  supabase client
```

- `repository.ts` is the **only** place that references table/column names. It maps rows → domain types (`snake_case` → `camelCase`).
- Use the **server client** (`@/lib/supabase/server`) by default — it runs as the user, so RLS applies.
- `@/lib/supabase/admin` bypasses RLS. Only for trusted backend jobs/webhooks, never with user-supplied filters, and always after an explicit authorization check.
- Check `error` on every Supabase call; wrap in `AppError` with `cause`.

Functions:

- `create_family(currency, timezone) → uuid` — caller must be a `parent` with no membership; raises `JA401` / `JA403` / `JA409`, `22023` for an unknown timezone.
- `register_child(child_id, family_id, nickname, pin, consent, invitation_id default null)` — approved parent of the family adds a child-role profile with no membership. With `invitation_id`, locks the invitation `for update` and requires it `pending` and unexpired, then marks it `accepted` (`accepted_by`, `child_id`, `family_id`) in the same transaction. Clears `parent_email` on the accepted invitation. Overwrites any stale `child_credentials` row and clears the child's lock state. Raises `JA403` (not a parent of the family, or no consent), `22023` (PIN not 4–6 digits, nickname not 1–20 letters, digits, spaces or `_ . ' -`), `JA404` (invitation missing, used or expired), `JA409` (child unavailable or nickname taken). Audits `child.added` and, with an invitation, `invitation.accepted`.
- `set_child_pin(child_id, pin)` — `is_parent_of` caller; sets the PIN and clears every lock (all `child_pin_attempts` rows and the safety cap). Audits `child.pin_reset`. The service then rotates the child's password and calls `revoke_user_sessions`.
- `remove_child(child_id) → boolean` — approved parent of the child's family. Membership → `removed`, `nickname_key` freed, profile nickname cleared, PIN credentials and attempts deleted, learning progress deleted (all six learning tables), audit `child.removed`; idempotent for an already-removed child of the same family. Returns whether the auth identity may be deleted: false once the child has any `ledger_entries` row, so the identity is kept, disabled (ADR 0007). `ledger_entries.child_id` is `on delete restrict`, so history is never cascade-deleted.
- `rename_child(child_id, nickname)` — approved parent; same nickname rules as `register_child`; JA409 when taken; audit `child.renamed` with from/to.
- `update_family_timezone(timezone)` — approved parent; must exist in `pg_timezone_names`; audit `family.updated`.
- `complete_parent_profile(date_of_birth, country, gender)` — signed-in parent only (JA403 otherwise); 18 or over, two-letter country, known gender (22023); upsert that keeps the first `completed_at`.
- `verify_child_pin(family_code, nickname, pin, source_hash) → table(child_id, status)` — **service_role only**. Normalises the code (upper, no spaces/hyphens) and nickname (`lower(btrim)`). `status` is `ok` (child_id set), `invalid` (unknown family/nickname, removed child or wrong PIN) or `locked` (this source locked, or the child frozen by the safety cap). Never raises for a bad sign-in so the counters commit. Per source: every 5th consecutive wrong PIN locks that source; lock *n* lasts 15 min × 2^(n−1), capped at 24 hours; a success from that source clears its row. Across sources: 100 wrong PINs within 24 h set `frozen_at` until `set_child_pin`. Each lock start writes `audit_log` `child.locked` (`details.scope` = `source` or `all`; no IP, no PIN). Unknown family or nickname spends a dummy bcrypt so timing reveals nothing.
- `revoke_user_sessions(user_id) → integer` — **service_role only**; deletes the user's `auth.sessions` rows (refresh tokens and MFA claims cascade) and returns the count. Call only after the service's own authz.
- `create_invitation(nickname, parent_email, token_hash, code_hash) → uuid` — **service_role only**; trims and validates the nickname (1–20 letters, digits, spaces or `_ . ' -`, else `22023`), stores a `pending` invitation expiring in 7 days. Callers hash the token and code first.
- `find_invitation(hash) → table(id, nickname)` — **service_role only**; the service calls it after `assertRole("parent")` and a per-parent rate limit. Matches `token_hash` or `code_hash` of a `pending`, unexpired invitation, else no rows.
- `list_my_invitations() → table(id, nickname, created_at, expires_at)` — `authenticated` only. The caller's `pending`, unexpired invitations whose `parent_email` matches their own `auth.users.email` case-insensitively, only when that email is confirmed and the caller's profile role is `parent`; newest first, at most 50. Never returns the email. Only safe with **Confirm email** and **Secure email change** on in the hosted project (`docs/auth.md`, Hosted setup); locally sign-up auto-confirms. Partial index `invitations_pending_parent_email_idx` on `lower(parent_email)`. The service also uses it to check an invitation id before accepting by id.
- Learning (ADR 0009), each `authenticated` only and refusing anyone but an approved child (`JA401` signed out, `JA403` otherwise, `22023` for malformed input), through the internal `learning_child_family()` (no grants):
  - `start_mission(mission_key, content_version) → uuid` — returns the open attempt for that mission (locked `for update`), abandons it when the content version is newer, refuses an older version (`JA409`). A per-child advisory lock stops a double tap opening two. At most 40 starts in 24 hours (`JA429`); resuming is never capped.
  - `record_step_result(attempt_id, step_key, phase, step_type, skill_key, correct, hints_used, tries) → boolean` — own `started` attempt only (`JA403`); false when the step and phase are already recorded or the attempt is finished. At most 20 results per attempt (`JA429`). Raises the skill to 2 (right) or 1, never lowers it, and adds to the evidence counters (a replay never counts as a first try).
  - `complete_mission(attempt_id, occurred_at default null) → boolean` — own attempt with at least one result (`22023`), not abandoned (`JA409`); false when already completed. `completed_at` is `resolve_occurred_at(occurred_at)`, never before `started_at`. Schedules a first review (box 1, the family day after that time) for every skill the attempt touched.
  - `record_practice_result(item_key, skill_key, correct, hints_used, tries, occurred_at default null) → boolean` — the family day and `answered_at` come from `resolve_occurred_at(occurred_at)`, so a queued answer counts on the day it was made. One result per item per family day (false on repeat), at most 60 a day (`JA429`). A due review moves up a box when right first try without hints (and the skill becomes Got it), stays when right with help, and drops to box 1 when wrong; a review that isn't due changes nothing.
  - `complete_checkin(content_version, question_count, correct_count) → boolean` — once per child; false on repeat.

  - `guide_start_conversation(child_id, entry, context_key) → uuid` — **service_role only**; the child must be approved with the guide on (`JA403`).

  - `guide_find_turn(child_id, client_message_id) → table(conversation_id, reply_id)` — **service_role only**; the turn stored for a re-sent question, or no row. `askGuide` calls it after the guide-access checks and returns the stored reply before any rate limit or model call.
  - `guide_usage_since(since) → table(model, token sums)` — **service_role only**; feeds the daily and monthly budgets.
  - `rate_guide_message(message_id, rating smallint)` — the child, on a guide reply in their own chat. `JA401`, `JA403`, `22023`.
  - `blank_old_guide_text() → int` — **cron only, no grants**; `pg_cron` job `blank-old-guide-text` daily at 03:17 UTC; writes a `job_runs` row.
  - `remove_child` also deletes the child's guide chats and switch.
- `family_today(family_id, now default now()) → date` — the family's local date (security invoker; null for a family the caller can't see).
- `allowance_due_on(anchor, frequency, index) → date` — `immutable`. Weekly: `anchor + 7*index`; monthly/quarterly/annual: `anchor + index*1/3/12 months` (Postgres clamps month-end, e.g. Jan 31 → Feb 28 → Mar 31). Always stepped from the anchor, never from the previous date.
- `generate_for_schedule(schedule_id, today) → int` — **internal; service_role only** (called by definer functions and the slice 2 generator job; the e2e suite fast-forwards with it through the admin client, as the demo clock will). Locks the schedule; only `active` schedules generate. Inserts every period with `allowance_due_on(anchor_on, frequency, next_index) <= today` (on conflict do nothing, current `amount_minor`), advances `next_index`, returns rows inserted.
- `generate_due_occurrences(now default now()) → int` — **cron only, no grants**. Scheduled by `pg_cron` as `generate-due-occurrences` at `5 * * * *` (the migration creates the extension and the job wherever `pg_cron` is available, which includes hosted Supabase; otherwise it warns and skips). The job command is `set local statement_timeout = '60s'; select public.generate_due_occurrences()`: the timeout must be set before the statement starts, so it lives in the command, not the function. Writes a `job_runs` row (`details`: `inserted`, `failed`, `errors` with `schedule_id`, `sqlstate` and `message` cut to 200 characters). For schedules whose child is still an approved child member: auto-resumes paused schedules with `paused_through < family today` (`next_index` = first period after `paused_through`, pause cleared, `audit_log` `allowance.resumed` with `auto`), then generates each active schedule up to its family's today. Each schedule runs in its own exception block (locked `skip locked`); any failure ends the run as `error` while the others still generate. Returns rows inserted.
- `allowance_next_due_on(schedule_id) → date` — next ungenerated period's due date; when paused through a date, the first period after it; null when stopped or paused until resumed. `JA403` unless the child or their parent.
- `create_allowance(child_id, amount_minor, frequency, first_on) → uuid`, `change_allowance(schedule_id, amount_minor, frequency, next_on)`, `pause_allowance(schedule_id, through, message)`, `resume_allowance(schedule_id)`, `stop_allowance(schedule_id)` — parent-only (`is_parent_of`, else `JA403`); each locks the schedule (create derives `family_id` from the child's approved membership; the others use the schedule's `family_id`), writes `audit_log` `allowance.created|changed|paused|resumed|stopped` and returns the schedule id. Dates use `family_today`. Amounts are 1..100000000000 and every date a parent picks is at most family today + 366 (`22023`). Create: `JA409` if an active or paused schedule exists, `22023` for a bad amount/frequency or `first_on` before today. Create and change generate at the end, so a date of today is due at once. Change, pause and stop first catch up generation to today; change then requires `next_on >= today`, after the last generated `due_on` and, while paused through a date, after `paused_through` (`22023`) and re-anchors (`anchor_on = next_on`, `next_index = 0`), except when the frequency is unchanged and `next_on` is the current next due date: then the anchor and `next_index` are kept, so a 31st stays the 31st after a short month. Generated occurrences keep their amount. Pause: only from `active` (else `JA409`), `through` null or today..today + 366, message trimmed (≤ 140). Resume (only from `paused`, else `JA409`): skips the periods inside the pause (before today and, for a dated pause, through `paused_through`), so paused periods are never paid, then generates; a dated pause that already ended keeps the periods after it, like the job's auto-resume. Stop is terminal; already-due occurrences stay due. Change/stop on a stopped schedule: `JA409`.
- `notify_parents(child_id, kind, source_type, source_id, window_key, payload) → int` / `notify_child(...) → int` — **internal, no grants** (call from other definer functions in the same transaction). Parents: one row per approved parent of the child's approved family; child: one row to the approved child. `on conflict do nothing` on the dedupe index. Each returns the rows it inserted (0 for a deduplicated repeat), so callers count notices without scanning `notifications`.
- `lock_occurrence_for_parent(occurrence_id) → allowance_occurrences` — **internal, no grants**. Locks the occurrence `for update`; `JA403` unless the caller is a parent of its child, also when it does not exist.
- `confirm_handover(occurrence_id, cash_minor, saved_minor, idempotency_key) → text` — parent-only (`JA403`). Locks the occurrence; a `confirmed` one returns `already_confirmed` and one marked not given (`closed`) returns `not_given`, posting nothing (exactly once); the app shows `not_given` as a conflict, not success. Requires cash, saved in 0..100000000000, sum (computed as numeric, so no overflow) > 0 and ≤ the occurrence amount, and a non-blank key (`22023`; the key is not stored). Then takes the child's ledger advisory lock (see Lock order). Inserts one `allowance_in` entry per non-zero jar (cash → Spend, saved → Save; keys `occurrence:<id>:spend|save`), sets `confirmed` with `shortfall_minor` = amount − sum, who and when. Returns `confirmed`.
- `mark_not_given(occurrence_id) → text` — parent-only (`JA403`). Locks the occurrence; a non-`due` one returns `already_handled`. Otherwise sets `closed` (with who and when), posts no ledger rows, writes `audit_log` `allowance.not_given`, returns `closed`.
- `lock_gift_for_parent(gift_id) → parent_gifts` — **internal, no grants**. Locks the gift `for update`; `JA403` unless the caller is a parent of its child, also when the gift does not exist.
- `create_gift(child_id, amount_minor, give_on, note, idempotency_key default null) → uuid` (null key → a fresh random one, for older callers), `update_gift(gift_id, amount_minor, give_on, note) → uuid`, `cancel_gift(gift_id) → uuid` — parent-only (`JA403`); create derives `family_id` from the child's approved membership, the others lock the gift. Writes `audit_log` `gift.created|updated|cancelled` (details hold `has_note`, not the note). Note trimmed, empty → null, over 140 → `22023`; amount outside 1..100000000000 → `22023`. Create: a blank key or one over 200 chars → `22023`; a key this parent already used for this child returns that gift's id (no insert, no audit, no date re-check), and for another child → `JA409`; `give_on` outside family today..today + 366 → `22023`. Update: a changed `give_on` outside today..today + 366 → `22023` (an unchanged past date of a due gift is kept). Update and cancel: `JA409` unless `pending`.
- `confirm_gift_handover(gift_id, cash_minor, saved_minor, idempotency_key) → text` — parent-only (`JA403`). Locks the gift; a `given` gift returns `already_confirmed` and a `cancelled` one returns `cancelled`, posting nothing; the app shows `cancelled` as a conflict, not success. `give_on` after family today → `JA409`. Requires cash, saved in 0..100000000000, sum > 0 and ≤ 100 × planned amount, and a non-blank key (`22023`; the key is not stored). Then takes the child's ledger advisory lock (see Lock order). Inserts one `parent_gift_in` entry per non-zero jar (`source_type parent_gift`, label = note or `Gift`, keys `parent_gift:<id>:spend|save`), then sets `given` with who and when. No shortfall. Returns `confirmed`.
- `list_due_for_parent(child_id) → table(kind, id, due_on, amount_minor, note)` — `kind` is `allowance` (occurrences with `status = due`) or `gift` (pending, `give_on <=` family today); oldest first. **`JA403` unless `is_parent_of`**, including for the child: it is the secrecy gate for due counts.
- `set_allow_negative_spend(child_id, allowed) → void` — parent-only (`JA403`); upserts `child_settings` (`family_id` from the child's approved membership), audits `settings.overspend` with `{allowed}`.
- `set_money_rule(child_id, kind, period, amount_minor) → void` — parent-only (`JA403`). A null amount deletes the rule (audit `rule.cleared`, only if one existed); otherwise upsert (audit `rule.set`). Details `{kind, period, amount_minor}`. Unknown kind or period, or amount outside 1..100000000000: `22023`.
- `rule_window_start(family_id, period, at) → timestamptz` — **internal, no grants**. Start of the Monday-based `week` or the `month` containing `at` in the family timezone; null for `item`. Purchase and withdrawal functions use it to sum a window.
- `held_spend(child_id) → bigint` — Spend held by pending deposits. `JA403` unless self or parent of.
- `reserved_save(child_id) → bigint` — Save promised to `pending` or `approved` withdrawals. `JA403` unless self or parent of.
- `available_save(child_id)` / `available_spend(child_id) → bigint` — Save minus `reserved_save`; Spend minus `held_spend`. `JA403` unless self or parent of.
- `request_window_total(child_id, kind, statuses[], window_start) → bigint` — **internal, no grants**. Sum of `requests.amount_minor` of that kind and status list with `occurred_at >= window_start` (all time when null). The single counter for withdrawal caps, auto-approve and deposit auto-confirm.
- `create_withdrawal(child_id, amount_minor, reason, idempotency_key) → jsonb` — child only (`JA403`). Amount outside 1..100000000000, reason (trimmed, empty → null) over 140, blank key or one over 200 → `22023`. Takes the ledger advisory lock. A repeated `(child, key)` returns `{status: <current status>, request_id}` (`JA409` if that key is a deposit). `amount > available_save` → `{status: over_available, available_minor}`. Each `withdrawal_cap` rule (item, week, month order): `request_window_total(pending, approved, handed_over) + amount > cap` (item: `amount > cap`) → `{status: over_cap, period, cap_minor, used_minor}`. Else inserts `pending`; if at least one `withdrawal_auto_approve` rule exists and all pass (approved + handed_over total + amount ≤ limit) it is `approved`, `auto true`, no notice; otherwise `notify_parents('withdrawal_requested', {amount_minor, reason})`. Returns `{status: pending|approved, request_id}`.
- `decide_withdrawal(request_id, approve, note) → text` — parent only (`JA403`, also for a missing request). Locks the request, then the ledger lock. Not `pending` → `already_decided`. Approve needs `amount <= balance(save) − reserved_save + amount`, else `over_available` (stays pending). Sets `decided_by/at`, note (trimmed, ≤140, else `22023`), `notify_child('withdrawal_decided', {amount_minor, approved})`. Returns `approved|rejected|already_decided|over_available`.
- `complete_request(request_id, idempotency_key) → text` — parent only (`JA403`); key not stored, blank or over 200 → `22023`. Locks the request, then the ledger lock. `handed_over` or `confirmed` → `already_completed`; otherwise only an `approved` withdrawal or a `pending` deposit proceeds (any other → `not_approved`) to `post_request`. Returns `completed|already_completed|not_approved|over_available`. Rules are not re-checked (a lowered cap does not block an approved hand-over).
- `create_deposit(child_id, amount_minor, idempotency_key) → jsonb` — child only (`JA403`). Amount outside 1..100000000000, blank key or one over 200 → `22023`. Takes the ledger advisory lock. A repeated `(child, key)` returns `{status: <current status>, request_id}` (`JA409` if that key is a withdrawal). `amount > available_spend` → `{status: over_available, available_minor}`. Else inserts `pending` (holds Spend via `held_spend`); if at least one `deposit_auto_confirm` rule exists and all pass (`request_window_total(deposit, {confirmed})` + amount ≤ limit; item: amount ≤ limit) it calls `post_request` in the same transaction and sets `confirmed`, `auto true`, no notice; otherwise `notify_parents('deposit_requested', {amount_minor})`. Returns `{status: pending|confirmed, request_id}`.
- `decide_deposit(request_id, note) → text` — parent only (`JA403`, also for a missing request); reject only ("Didn't get it"; confirming is `complete_request`). Not a deposit or note over 140 → `22023`. Locks the request, then the ledger lock. Not `pending` → `already_decided`. Sets `rejected`, `decided_by/at`, note (trimmed), posts nothing (the hold is released), `notify_child('deposit_decided', {amount_minor, approved: false})`. Returns `rejected|already_decided`.
- `post_request(request_id, actor) → text` — **internal, no grants**: the only path that posts a request to the ledger. Withdrawal: re-checks `amount <= balance(save) − (reserved_save − amount)`, inserts `withdrawal_out` (save) and `withdrawal_in` (spend), `source_type request`, label = reason or `Taken out of Save`, keys `request:<id>:out|in`, sets `handed_over`, `completed_by/at`. Deposit: re-checks `amount <= balance(spend) − (held_spend − amount)`, inserts `deposit_out` (spend) and `deposit_in` (save), label `Put into Save`, same keys, sets `confirmed`, `completed_by/at` (an auto-confirm records the child as actor). Either refusal returns `over_available`; success `completed`; any other kind raises `22023`.
- `cancel_request(request_id) → text` — the child cancels their own `pending` request; a parent cancels a `pending` or `approved` withdrawal (parents decide deposits via `decide_deposit`: `22023`). Takes only the row lock (no ledger lock), posts nothing. Returns `cancelled|already_closed`; `JA403` otherwise.
- `withdrawal_cap_remaining(child_id) → bigint` — the smallest room left under the child's `withdrawal_cap` rules: each week or month cap minus `request_window_total(pending, approved, handed_over)` in its window, floored at 0; an item cap counts as unused; `null` when the child has no cap. `JA403` unless self or parent of. The child's take-out sheet uses it to show how much can be asked for.
- `record_purchase(child_id, amount_minor, label, idempotency_key, occurred_at default null) → jsonb` — child only (`is_self`, approved child membership, else `JA403`). Amount outside 1..100000000000, label (trimmed, empty → null) over 60, or a blank key or one over 200 characters → `22023`. Takes the child's ledger advisory lock (no source row). A repeated key (`purchase:<child>:<key>`) returns `{status: recorded, entry_id, notices: 0}` with the original entry, without re-checking Spend or limits. Otherwise `free = balance(spend) − held_spend`; refuses with `{status: not_enough_spend, free_minor}` (posting nothing) when overspend is off and `amount > free`, or when it is on, `held_spend > 0` and Spend would drop below `held_spend`. Inserts the `purchase` (`spend`, `out`, `source_type diary`, `created_by` caller, `occurred_at` = `resolve_occurred_at(occurred_at)`), then `evaluate_spend_limits`. A backdated purchase lands on its own diary day, spending-limit window and undo window; the Spend check uses the current balance. Returns `{status: recorded, entry_id, notices}`.
- `record_purchase_at(child_id, amount_minor, label, idempotency_key, now) → jsonb` — **internal, no grants**: the clock seam behind `record_purchase` (pgTAP, demo clock); the purchase's `occurred_at` and limit windows use `now`.
- `resolve_occurred_at(p) → timestamptz` — **internal, no grants**: when a child action happened (the outbox route derives it from the action's age on the server clock). Null or any future time → `now()`; more than 7 days back → `22023` (a backstop); otherwise `p`. Used by `record_purchase`, `record_practice_result` and `complete_mission`. `start_mission` stays online-only (it returns the attempt id); `record_step_result` and `complete_checkin` have no day logic and take no time.
- `send_handover_reminders(now default now()) → int` — **cron only, no grants**; `pg_cron` job `send-handover-reminders` at `7 * * * *` (same guard and `statement_timeout` command as `generate-due-occurrences`). For each allowance occurrence still `due`, with `d` = family today − `due_on`: `d = 0` notifies the parents and the child (`allowance_due`, window `<id>:due`); `d > 0 and d % 3 = 0` notifies the parents (`handover_reminder`, window `<id>:<family date>`). Source `allowance_occurrence`, payload `{amount_minor, due_on, days_overdue}`. Reruns add nothing; an occurrence first seen late waits for its next 3-day mark; paused schedules still remind; confirmed or closed occurrences never do. Returns rows inserted.
- `mark_notifications_read(ids uuid[] default null) → int` — `authenticated`; sets `read_at` on the caller's own unread notices (the given ids, or all when null). The only write path: `notifications` has no update grant. Returns the count.
- `unread_notification_count() → int` — `authenticated`; the caller's unread notices in families they are an approved member of.
- `evaluate_spend_limits(entry_id) → int` — **internal, no grants**; called under the ledger lock. Per `spend_limit` rule of the child: `item` notifies when the amount is over the limit (window `spend_limit:item:<entry_id>`); `week`/`month` sum every live (not reversed) recorded Spend purchase from `rule_window_start` up to the next local window start (exclusive), this one included (`after`; `occurred_at` is the transaction start, so a purchase that waited on the ledger lock can carry an earlier time than one already committed: it still counts that one within its window, and never one from the next window), and notify when `after − amount <= limit < after` (window `spend_limit:<period>:<window start as a family-local date>`). `notify_parents` kind `limit_exceeded`, source `ledger_entry`, payload `{amount_minor, limit_minor, period, total_minor}`. Returns the number of rules whose notice it wrote, from the `notify_parents` row counts (a window already noticed is deduplicated and not counted). Undo never adds or retracts a notice.
- `undo_purchase(entry_id) → text` — the entry's child only, with an approved child membership in the entry's family (`JA403`, also for a missing entry); not a purchase → `22023`. Locks the entry `for no key update`, then the ledger advisory lock. Returns `already_undone` if reversed, `too_late` if `occurred_at < now() − 24 hours`, else inserts a `reversal` (`in`, same jar, mode and amount, `reverses_entry_id`, key `reversal:<entry_id>`) and returns `undone`. `undo_purchase_at(entry_id, now)` is its **internal, no grants** clock seam.
- `hit_rate_limit(key, window, max) → boolean` — **service_role only**; counts a hit in the `date_bin(window, now(), epoch)` window and returns `true` while the count is within `max`.

Lock order: ledger writers lock the source row first, then the child's ledger advisory lock; never the reverse. The source row lock (`lock_occurrence_for_parent`, `lock_gift_for_parent`, `for update`) comes first because the row says which child it belongs to; then `pg_advisory_xact_lock(hashtextextended('ledger:' || child_id, 0))`; then the ledger inserts. Every later writer (purchases, savings requests) follows the same order, so balance checks are serialised per child without deadlocks. The request functions follow it: `decide_withdrawal`, `complete_request` and `decide_deposit` lock the `requests` row first (`for update`), then the ledger advisory lock; `cancel_request` takes only the row lock, since it posts nothing; `create_withdrawal` and `create_deposit` have no row yet, so they take the ledger lock first and the `(child, key)` unique index settles a repeated key. `post_request` runs under both locks and is never called directly. Purchases and requests share the one ledger lock, so a purchase racing a deposit sees the hold. Future reversal writers (undo of any ledger entry) lock the entry row first (`for no key update`), then the ledger advisory lock, as `undo_purchase` does.
