# Database (Supabase)

Postgres via Supabase. Schema is managed **only** through SQL migrations in `supabase/migrations/`. Never edit the schema from the dashboard in a shared environment.

## Local workflow

```bash
pnpm db:start                 # start local Supabase (Docker required); prints URL + keys
pnpm exec supabase status     # show keys again → copy into .env.local
pnpm db:migration add_thing   # create supabase/migrations/<ts>_add_thing.sql
pnpm db:reset                 # rebuild local DB from migrations + seed.sql
pnpm db:types                 # regenerate types from local DB
pnpm db:types:linked          # regenerate types from linked hosted project
pnpm db:stop
```

Studio: http://127.0.0.1:54323 · Inbucket (auth emails): http://127.0.0.1:54324

## Deploying migrations

```bash
pnpm exec supabase link --project-ref <ref>
pnpm db:push                  # always --linked (explicit; CLI default is changing)
```

Normally you don't run this. Supabase's GitHub integration watches `main` (Supabase → Project Settings → Integrations → GitHub, working directory `.`, production branch `main`, "Deploy to production" on, preview branches off) and applies new migrations to the hosted project on every merge. Only `main` deploys; PRs never touch a hosted database. Status and logs are in the Supabase dashboard. The commands above are the fallback if the integration is off or a deploy fails.

Because `supabase/config.toml` has a `[remotes.production]` block naming the project, the integration also syncs the `[auth]`, `[api]`, `[db]` and `[storage]` settings from that block on each deploy, so auth settings are code. Seeds are never applied to production.

Each migration file runs in one transaction (so no `create index concurrently`), and a migration older than the latest applied one still runs, with a warning. Migrations must be forward-only and expand/contract, because the integration and the Vercel build run side by side; to undo, write a new migration.

## Migration rules

1. One logical change per migration. Name it `snake_case` describing the change.
2. **Every table in `public` gets RLS enabled in the same migration that creates it.** No exceptions.
3. Write explicit policies per operation (`select`, `insert`, `update`, `delete`) and role (`to authenticated`). No catch-all `for all` policies unless genuinely identical.
4. Use `(select auth.uid())` (wrapped) in policies — it's evaluated once per query, not per row.
5. Index every foreign key and every column used in RLS predicates.
6. Standard columns: `id uuid primary key default gen_random_uuid()`, `created_at timestamptz not null default now()`, `updated_at timestamptz not null default now()` + `public.set_updated_at()` trigger.
7. Functions: `set search_path = ''` and fully-qualify names. `security definer` only when needed, and never exposing it to callers who could abuse it.
8. Comment non-obvious tables/columns (`comment on …`).
9. After any migration: `pnpm db:reset && pnpm db:types`, commit the regenerated types.
10. Destructive changes (drop/rename column) ship in two deploys: stop using it in code → then drop.

## Data access in code

```
service.ts  ──►  repository.ts  ──►  supabase client
```

- `repository.ts` is the **only** place that references table/column names. It maps rows → domain types (`snake_case` → `camelCase`).
- Use the **server client** (`@/lib/supabase/server`) by default — it runs as the user, so RLS applies.
- `@/lib/supabase/admin` bypasses RLS. Only for trusted backend jobs/webhooks, never with user-supplied filters, and always after an explicit authorization check.
- Check `error` on every Supabase call; wrap in `AppError` with `cause`.

Functions:

- `create_family(currency, timezone) → uuid` — caller must be a `parent` with no membership; raises `JA401` / `JA403` / `JA409`, `22023` for an unknown timezone.
- `register_child(child_id, family_id, nickname, pin, consent, invitation_id default null)` — approved parent of the family adds a child-role profile with no membership. With `invitation_id`, locks the invitation `for update` and requires it `pending` and unexpired, then marks it `accepted` (`accepted_by`, `child_id`, `family_id`) in the same transaction. Clears `parent_email` on the accepted invitation. Overwrites any stale `child_credentials` row and clears the child's lock state. Raises `JA403` (not a parent of the family, or no consent), `22023` (PIN not 4–6 digits, nickname not 1–20 letters, digits, spaces or `_ . ' -`), `JA404` (invitation missing, used or expired), `JA409` (child unavailable or nickname taken). Audits `child.added` and, with an invitation, `invitation.accepted`.
- `set_child_pin(child_id, pin)` — `is_parent_of` caller; sets the PIN and clears every lock (all `child_pin_attempts` rows and the safety cap). Audits `child.pin_reset`. The service then rotates the child's password and calls `revoke_user_sessions`.
- `remove_child(child_id) → boolean` — approved parent of the child's family. Membership → `removed`, `nickname_key` freed, profile nickname cleared, PIN credentials and attempts deleted, learning progress deleted (all six learning tables), audit `child.removed`; idempotent for an already-removed child of the same family. Returns whether the auth identity may be deleted: false once the child has any `ledger_entries` row, so the identity is kept, disabled (ADR 0007). `ledger_entries.child_id` is `on delete restrict`, so history is never cascade-deleted.
- `rename_child(child_id, nickname)` — approved parent; same nickname rules as `register_child`; JA409 when taken; audit `child.renamed` with from/to.
- `update_family_timezone(timezone)` — approved parent; must exist in `pg_timezone_names`; audit `family.updated`.
- `complete_parent_profile(date_of_birth, country, gender)` — signed-in parent only (JA403 otherwise); 18 or over, two-letter country, known gender (22023); upsert that keeps the first `completed_at`.
- `verify_child_pin(family_code, nickname, pin, source_hash) → table(child_id, status)` — **service_role only**. Normalises the code (upper, no spaces/hyphens) and nickname (`lower(btrim)`). `status` is `ok` (child_id set), `invalid` (unknown family/nickname, removed child or wrong PIN) or `locked` (this source locked, or the child frozen by the safety cap). Never raises for a bad sign-in so the counters commit. Per source: every 5th consecutive wrong PIN locks that source; lock *n* lasts 15 min × 2^(n−1), capped at 24 hours; a success from that source clears its row. Across sources: 100 wrong PINs within 24 h set `frozen_at` until `set_child_pin`. Each lock start writes `audit_log` `child.locked` (`details.scope` = `source` or `all`; no IP, no PIN). Unknown family or nickname spends a dummy bcrypt so timing reveals nothing.
- `revoke_user_sessions(user_id) → integer` — **service_role only**; deletes the user's `auth.sessions` rows (refresh tokens and MFA claims cascade) and returns the count. Call only after the service's own authz.
- `create_invitation(nickname, parent_email, token_hash, code_hash) → uuid` — **service_role only**; trims and validates the nickname (1–20 letters, digits, spaces or `_ . ' -`, else `22023`), stores a `pending` invitation expiring in 7 days. Callers hash the token and code first.
- `find_invitation(hash) → table(id, nickname)` — **service_role only**; the service calls it after `assertRole("parent")` and a per-parent rate limit. Matches `token_hash` or `code_hash` of a `pending`, unexpired invitation, else no rows.
- `list_my_invitations() → table(id, nickname, created_at, expires_at)` — `authenticated` only. The caller's `pending`, unexpired invitations whose `parent_email` matches their own `auth.users.email` case-insensitively, only when that email is confirmed and the caller's profile role is `parent`; newest first, at most 50. Never returns the email. Only safe with **Confirm email** and **Secure email change** on in the hosted project (`docs/auth.md`, Hosted setup); locally sign-up auto-confirms. Partial index `invitations_pending_parent_email_idx` on `lower(parent_email)`. The service also uses it to check an invitation id before accepting by id.

  - `start_mission(mission_key, content_version) → uuid` — returns the open attempt for that mission (locked `for update`), abandons it when the content version is newer, refuses an older version (`JA409`). A per-child advisory lock stops a double tap opening two. At most 40 starts in 24 hours (`JA429`); resuming is never capped.

  - `record_practice_result(item_key, skill_key, correct, hints_used, tries) → boolean` — one result per item per family day (false on repeat), at most 60 a day (`JA429`). A due review moves up a box when right first try without hints (and the skill becomes Got it), stays when right with help, and drops to box 1 when wrong; a review that isn't due changes nothing.

- `family_today(family_id, now default now()) → date` — the family's local date (security invoker; null for a family the caller can't see).
- `allowance_due_on(anchor, frequency, index) → date` — `immutable`. Weekly: `anchor + 7*index`; monthly/quarterly/annual: `anchor + index*1/3/12 months` (Postgres clamps month-end, e.g. Jan 31 → Feb 28 → Mar 31). Always stepped from the anchor, never from the previous date.
- `generate_for_schedule(schedule_id, today) → int` — **internal; service_role only** (called by definer functions and the slice 2 generator job; the e2e suite fast-forwards with it through the admin client, as the demo clock will). Locks the schedule; only `active` schedules generate. Inserts every period with `allowance_due_on(anchor_on, frequency, next_index) <= today` (on conflict do nothing, current `amount_minor`), advances `next_index`, returns rows inserted.
- `generate_due_occurrences(now default now()) → int` — **cron only, no grants**. Scheduled by `pg_cron` as `generate-due-occurrences` at `5 * * * *` (the migration creates the extension and the job wherever `pg_cron` is available, which includes hosted Supabase; otherwise it warns and skips). The job command is `set local statement_timeout = '60s'; select public.generate_due_occurrences()`: the timeout must be set before the statement starts, so it lives in the command, not the function. Writes a `job_runs` row (`details`: `inserted`, `failed`, `errors` with `schedule_id`, `sqlstate` and `message` cut to 200 characters). For schedules whose child is still an approved child member: auto-resumes paused schedules with `paused_through < family today` (`next_index` = first period after `paused_through`, pause cleared, `audit_log` `allowance.resumed` with `auto`), then generates each active schedule up to its family's today. Each schedule runs in its own exception block (locked `skip locked`); any failure ends the run as `error` while the others still generate. Returns rows inserted.
- `allowance_next_due_on(schedule_id) → date` — next ungenerated period's due date; when paused through a date, the first period after it; null when stopped or paused until resumed. `JA403` unless the child or their parent.
- `create_allowance(child_id, amount_minor, frequency, first_on) → uuid`, `change_allowance(schedule_id, amount_minor, frequency, next_on)`, `pause_allowance(schedule_id, through, message)`, `resume_allowance(schedule_id)`, `stop_allowance(schedule_id)` — parent-only (`is_parent_of`, else `JA403`); each locks the schedule (create derives `family_id` from the child's approved membership; the others use the schedule's `family_id`), writes `audit_log` `allowance.created|changed|paused|resumed|stopped` and returns the schedule id. Dates use `family_today`. Amounts are 1..100000000000 and every date a parent picks is at most family today + 366 (`22023`). Create: `JA409` if an active or paused schedule exists, `22023` for a bad amount/frequency or `first_on` before today. Create and change generate at the end, so a date of today is due at once. Change, pause and stop first catch up generation to today; change then requires `next_on >= today`, after the last generated `due_on` and, while paused through a date, after `paused_through` (`22023`) and re-anchors (`anchor_on = next_on`, `next_index = 0`), except when the frequency is unchanged and `next_on` is the current next due date: then the anchor and `next_index` are kept, so a 31st stays the 31st after a short month. Generated occurrences keep their amount. Pause: only from `active` (else `JA409`), `through` null or today..today + 366, message trimmed (≤ 140). Resume (only from `paused`, else `JA409`): skips the periods inside the pause (before today and, for a dated pause, through `paused_through`), so paused periods are never paid, then generates; a dated pause that already ended keeps the periods after it, like the job's auto-resume. Stop is terminal; already-due occurrences stay due. Change/stop on a stopped schedule: `JA409`.
- `lock_occurrence_for_parent(occurrence_id) → allowance_occurrences` — **internal, no grants**. Locks the occurrence `for update`; `JA403` unless the caller is a parent of its child, also when it does not exist.
- `confirm_handover(occurrence_id, cash_minor, saved_minor, idempotency_key) → text` — parent-only (`JA403`). Locks the occurrence; a `confirmed` one returns `already_confirmed` and one marked not given (`closed`) returns `not_given`, posting nothing (exactly once); the app shows `not_given` as a conflict, not success. Requires cash, saved in 0..100000000000, sum (computed as numeric, so no overflow) > 0 and ≤ the occurrence amount, and a non-blank key (`22023`; the key is not stored). Then takes the child's ledger advisory lock (see Lock order). Inserts one `allowance_in` entry per non-zero jar (cash → Spend, saved → Save; keys `occurrence:<id>:spend|save`), sets `confirmed` with `shortfall_minor` = amount − sum, who and when. Returns `confirmed`.
- `mark_not_given(occurrence_id) → text` — parent-only (`JA403`). Locks the occurrence; a non-`due` one returns `already_handled`. Otherwise sets `closed` (with who and when), posts no ledger rows, writes `audit_log` `allowance.not_given`, returns `closed`.
- `lock_gift_for_parent(gift_id) → parent_gifts` — **internal, no grants**. Locks the gift `for update`; `JA403` unless the caller is a parent of its child, also when the gift does not exist.
- `create_gift(child_id, amount_minor, give_on, note) → uuid`, `update_gift(gift_id, amount_minor, give_on, note) → uuid`, `cancel_gift(gift_id) → uuid` — parent-only (`JA403`); create derives `family_id` from the child's approved membership, the others lock the gift. Writes `audit_log` `gift.created|updated|cancelled` (details hold `has_note`, not the note). Note trimmed, empty → null, over 140 → `22023`; amount outside 1..100000000000 → `22023`. Create: `give_on` outside family today..today + 366 → `22023`. Update: a changed `give_on` outside today..today + 366 → `22023` (an unchanged past date of a due gift is kept). Update and cancel: `JA409` unless `pending`.
- `confirm_gift_handover(gift_id, cash_minor, saved_minor, idempotency_key) → text` — parent-only (`JA403`). Locks the gift; a `given` gift returns `already_confirmed` and a `cancelled` one returns `cancelled`, posting nothing; the app shows `cancelled` as a conflict, not success. `give_on` after family today → `JA409`. Requires cash, saved in 0..100000000000, sum > 0 and ≤ 100 × planned amount, and a non-blank key (`22023`; the key is not stored). Then takes the child's ledger advisory lock (see Lock order). Inserts one `parent_gift_in` entry per non-zero jar (`source_type parent_gift`, label = note or `Gift`, keys `parent_gift:<id>:spend|save`), then sets `given` with who and when. No shortfall. Returns `confirmed`.
- `list_due_for_parent(child_id) → table(kind, id, due_on, amount_minor, note)` — `kind` is `allowance` (occurrences with `status = due`) or `gift` (pending, `give_on <=` family today); oldest first. **`JA403` unless `is_parent_of`**, including for the child: it is the secrecy gate for due counts.
- `hit_rate_limit(key, window, max) → boolean` — **service_role only**; counts a hit in the `date_bin(window, now(), epoch)` window and returns `true` while the count is within `max`.

Lock order: ledger writers lock the source row first, then the child's ledger advisory lock; never the reverse. The source row lock (`lock_occurrence_for_parent`, `lock_gift_for_parent`, `for update`) comes first because the row says which child it belongs to; then `pg_advisory_xact_lock(hashtextextended('ledger:' || child_id, 0))`; then the ledger inserts. Every later writer (purchases, savings requests) follows the same order, so balance checks are serialised per child without deadlocks.
