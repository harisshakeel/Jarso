## The ADR's "just add a folder" is wrong in four places

ADR 0012 says a second provider needs one adapter folder, one registry line and env vars, with no migration and no domain or UI change. The code disagrees:

1. **A migration is needed.** Four tables restrict the `provider` column to `('stripe','fake')`: `payment_customers`, `payment_setups`, `payments` and `payment_webhook_events` ([20261031064410_payments.sql:15](supabase/migrations/20261031064410_payments.sql#L15)).
2. **Saved cards don't fit cleanly.** The interface expects any provider to save a card and charge it later (`createHostedSetup` / `chargeSaved`). Razorpay can only do this through its recurring-payments product, which has extra rules (details below).
3. **Currency.** Family currency can be GBP, EUR, USD, INR, AUD, CAD or JPY ([site.ts:112](src/config/site.ts#L112)). A standard Razorpay account charges INR only unless international payments are enabled. So in practice Razorpay is for INR families; for anyone else the card options stay hidden, which the service already handles through `minimumChargeMinor`.
4. **Contract test.** [contract.test.ts](src/lib/payments/contract.test.ts) hard-codes GBP. Razorpay would fail it, so each adapter needs to declare its own test currency.

**How the adapter works:**
- **Paying now:** it creates a Razorpay Payment Link (a hosted payment page). Our payment id goes in `reference_id` and `notes.paymentId`, and the link uses `expire_by` and `callback_url`.
  - **Card only:** the link must offer card only (no UPI, net banking or wallets). Otherwise a payment would be wrongly shown as "paid by card" in the child's history.
  - **Expiry:** Razorpay's minimum link lifetime is 15 minutes, so the current 31-minute window works.
- **Cancel page:** Razorpay has no cancel URL. An abandoned link simply expires and sends a `payment_link.expired` event, so the "cancelled return" page is never reached on Razorpay.
- **Duplicate requests:** Razorpay has no idempotency-key header, so a retried request could create a second link. We rely on the existing reuse of an open link (`redirect_url`) and on the unique `provider_ref` index. Spike: check whether Razorpay itself rejects a repeated `reference_id`.
- **Webhooks:**
  - **Signature:** verify `X-Razorpay-Signature` (HMAC-SHA256 of the raw body) with a timing-safe compare.
  - **Duplicates:** use the `x-razorpay-event-id` header as the event id, which the existing replay guard already de-duplicates.
  - **Status mapping:** `payment_link.paid` → succeeded, `payment_link.expired` → expired, `payment_link.cancelled` → canceled. Ignore `payment.failed`, because the parent can retry on the same link, the same way Stripe Checkout behaves.
- **Live mode:** Razorpay events carry no `livemode` flag. The guard is the `rzp_test_` key prefix plus a webhook secret configured on the test-mode dashboard.
- **API client:** plain `fetch` with basic auth and an 8-second timeout, plus `node:crypto` for the signature. No SDK, since we only call a handful of endpoints.
- **Errors:** follow the Stripe adapter's `toAppError` pattern, so callers only ever see `AppError`.

**Tests:**

## Phase 2 (optional): auto charge on Razorpay

- **Saving a card:** a Registration Link (`subscription_registration/auth_links`, card method). The card is ready once a `token.confirmed` event arrives; we then fetch the token for the card brand and last 4.
- **Charging:** a new order plus `payments/create/recurring` each time. The result arrives asynchronously via `payment.captured` / `payment.failed`.
- **Removing a card:** delete the token.

**Risks:**
- Recurring payments must be enabled on the Razorpay account, which requires Razorpay's approval.
- In test mode, card tokens expire after 3 days, which makes the demo fragile.
- India's card-mandate rules (RBI) require a pre-debit notification, historically sent about 36 hours before the debit. That may mean charging ahead of the due date, which conflicts with the "charge on the due day" model. This needs checking against current Razorpay docs.
- Charges above ₹15,000 need the customer's extra authentication.

**Effort:** Phase 1 is about 1 day. Phase 2 is 2–3 days plus waiting for Razorpay to enable recurring payments.
