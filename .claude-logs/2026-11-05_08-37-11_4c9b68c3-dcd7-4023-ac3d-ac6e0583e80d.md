No, and it doesn't need to be. The Stripe key is never built into the APK, so you don't have to rebuild the app for this.

The only server setting baked into the APK is the address it calls, `EXPO_PUBLIC_API_URL`. The phone asks that server which payment options exist. The server then sends back Stripe, including its publishable key, but only if `STRIPE_PUBLISHABLE_KEY` is set on the server. So the key has to be added on whichever server the APK points to:

- **If the APK points at your laptop** (`http://<LAN IP>:3000`): add `STRIPE_PUBLISHABLE_KEY=pk_test_…` to `apps/web/.env.local` and restart `pnpm dev`.
- **If the APK points at a deployed site:** add it in that Vercel environment's variables and redeploy.

Then reopen the handover sheet and you should see two buttons, "Pay with Stripe" and "Pay with Razorpay".

If you're not sure which server the APK uses: an APK built locally with `pnpm build:apk` takes it from `apps/mobile/.env.local`. A cloud EAS build takes it from the EAS environment. You can see the EAS value with `! cd apps/mobile && eas env:list --environment preview`. The address isn't secret, but don't paste any key values here.

When the parent opens "Hand over to Tina", the sheet loads several things before showing the form: the family, the gift or allowance, the last cash/saved split, and the card payment options. The card payment options decide whether the "Or pay by card" card appears, and with which buttons.

**Before #131:** the form appeared as soon as the main details were in. The payment options came a moment later, so the card popped in and pushed "Confirm I handed it over" down (your first screenshot).

**Now:** the spinner stays up until the payment options are back too, so the form appears once with the card already in place. But payment options are optional, and on a slow or stalled connection that request can take 15 to 30 seconds before it gives up. So the wait is capped at **3 seconds**:

- **Back within 3 s** (the normal case): the form opens with the card in place, with no jump.
- **Still loading after 3 s:** the form opens without the card, so the parent can still confirm a cash handover. If the options arrive later, the card appears then, and only in that slow case can it still push Confirm down.
- **Request fails:** the form opens without the card, as before.
- **Phone offline:** the form opens straight away.

So at most the parent sees the spinner for 3 extra seconds on a bad connection. You can lower it (1–2 s gives more late pop-ins on slow networks) or raise it (5 s gives a longer spinner but fewer jumps). Do you want a different number, or is 3 seconds fine?

No API holds database connections open, so connections aren't what's making the app slow.

- **No direct database driver.** There's no `pg`, `postgres`, Prisma, Drizzle or Redis in any app or package. Every query goes through `supabase-js`, which sends one HTTP request per query to Supabase. Supabase's pooler owns the actual database connections, and nothing in our code can hold or leak one.
- **A new client per request is fine.** `createStatelessClient()` and the per-request bearer client are lightweight objects. The signing keys used to check sign-in tokens are cached for the whole server process (in `auth-js` 2.118.0), not per client, so building a new client doesn't add network calls.
- **Calls can't hang forever.** Every Supabase call has an 8 s cutoff (`apps/web/src/lib/timed-fetch.ts:4`) and returns a 503 after that. The 12–15 s waits on the phone are the server's own time plus the app's timeout.
- **Same region.** Vercel functions run in Tokyo (`hnd1`), and Supabase is in Tokyo too (`ap-northeast-1`), so database calls are short.

The slowness you saw came from the push sign-up loop. Each loop round was a full API request (token check plus database write), several per second, on top of everything else.
