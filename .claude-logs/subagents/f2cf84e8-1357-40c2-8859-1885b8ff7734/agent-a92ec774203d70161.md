**M1. A child account can get a password that a PIN reset doesn't remove**
- Where: `/home/ezio/Desktop/Work/8x/Jarso/supabase/config.toml:229` (`secure_password_change = false`), `/home/ezio/Desktop/Work/8x/Jarso/src/features/family/server/child-auth.ts:19-25`, and the `set_child_pin` function in `/home/ezio/Desktop/Work/8x/Jarso/supabase/migrations/20261028182920_invitations.sql:230-269`.
- Risk: anyone holding a child's session (the child, or a sibling on a shared tablet) can call `supabase.auth.updateUser({ password })` with the publishable key. They can then sign in with `<uuid>@child.jarso.invalid` plus that password through GoTrue or `/login`. This skips the PIN lockout and survives a parent's PIN reset. A PIN reset also doesn't end existing child sessions.
- Fix:
  - Add a GoTrue Password Verification hook (or a Custom Access Token hook) that rejects password sign-in when `app_metadata.jarso_role = 'child'`.
  - In `setChildPin`, after the RPC succeeds and parent authorization has passed, call admin `updateUserById(childId, { password: generateToken() })` and `admin.signOut` for the child, so a reset logs the child out everywhere.
  - Also reject the child email domain in `signInSchema`.

**M2. Anyone who knows the family code can keep every child in that family from signing in**
- This is the known lockout item, with my severity judgement.
- Where: `/home/ezio/Desktop/Work/8x/Jarso/src/features/family/server/service.ts:184` (`pin:family:${familyCode}`, 30 per hour) and `/home/ezio/Desktop/Work/8x/Jarso/supabase/migrations/20261028182920_invitations.sql:313-337` (the escalating 24-hour lock).
- Risk:
  - Anyone with the family code (it is shared between the children, so a classmate could have it) can send 30 requests an hour and block every child in the family, indefinitely.
  - Adding a nickname, they need only 5 requests a day to hold that child in a 24-hour lock.
  - A PIN reset clears the lock, but the attacker can re-lock it right away, and the "locked" response confirms the nickname exists. For a children's app this is a ready-made bullying tool.
- Fix:
  - Key the family limiter as `(familyCode, ip)` rather than just the family code.
  - Count lock failures per `(child, ip)`, and keep only a much higher global cap per child.
  - Write an `audit_log` row (`child.locked`) and notify the parent when a lock happens.
  - Return the same "invalid" status while locked unless the request comes from an IP that has already signed in successfully.

**M3. Personal data is kept indefinitely, against invariant 16**
- Where:
  - `/home/ezio/Desktop/Work/8x/Jarso/supabase/migrations/20261028182920_invitations.sql:27-40`: `parent_email` is kept after acceptance and on rows that are never accepted, and nothing ever sets the `'expired'` status.
  - `/home/ezio/Desktop/Work/8x/Jarso/src/features/family/server/service.ts:108-109,183`: rate-limit keys store the parent email in plain text (`invite:email:<email>`) and the IP addresses of signed-out children (`pin:ip:`, `invite:ip:`) in `usage_counters`, which is never cleaned up.
- Risk: invariant 16 says to store only a nickname and the parent email until approval. In practice the parent email and children's IPs are kept forever, in rows that grow without limit.
- Fix:
  - In `register_child`, set `parent_email = ''` (or make the column nullable and set it to null) when an invitation is accepted.
  - Add a pg_cron retention job that deletes or anonymises invitations past `expires_at` and deletes `usage_counters` rows older than about 2 days.
  - Hash the identifying part of each limiter key, e.g. `sha256(pepper || email)` and the same for IPs, before calling `hit_rate_limit`.

**M4. The public `/start` form can be used to send email to any address**
- Where: `/home/ezio/Desktop/Work/8x/Jarso/src/features/family/server/service.ts:106-137`, with the schema at `/home/ezio/Desktop/Work/8x/Jarso/src/features/family/schemas.ts:3-8,33-36`.
- Risk: anyone, without signing in, can make Jarso email any address, with 20 free-text characters (which could be a URL or a scam line) in both the subject and body. The per-email limit (3 a day) can be bypassed with `+tag` or dotted variants of the address, and the IP limit falls to rotating IPs. This damages the Resend sending domain's reputation and gives phishers a trusted sender.
- Fix:
  - Limit nicknames to letters, numbers, spaces and common name punctuation, e.g. `^[\p{L}\p{N} _.'-]+$`, which blocks `/` and `:`. Apply the same rule in `create_invitation`/`register_child`.
  - Don't put the nickname in the subject line (use a fixed one).
  - Normalise the email before using it as a limiter key (strip the `+tag`, lowercase).
  - Add a global daily cap, e.g. `invite:global` at about 200 a day, and consider a CAPTCHA (Turnstile) on `/start`.

**M5. The secret-scanning safety nets don't cover the new Resend key**
- Where: `/home/ezio/Desktop/Work/8x/Jarso/scripts/check-secrets.sh:6`, `/home/ezio/Desktop/Work/8x/Jarso/.claude/hooks/extract-log.py:22-52` and `/home/ezio/Desktop/Work/8x/Jarso/.gitleaks.toml`.
- Risk: `RESEND_API_KEY` is a new kind of credential. A bare `re_…` key in a prompt, log or commit is only caught if it appears on a `KEY=value` line. Nothing else redacts or blocks it in this public repo, and I couldn't confirm that gitleaks' default rules include Resend.
- Fix: add `re_[A-Za-z0-9_]{20,}` (a Resend key pattern) to all three: the pre-commit regex, `REDACTIONS`, and a `[[rules]]` entry in `.gitleaks.toml`.

### Low

**L1. `find_invitation` can be called directly by any signed-in user, skipping the service rate limit** (known item)
- Where: `/home/ezio/Desktop/Work/8x/Jarso/supabase/migrations/20261028182920_invitations.sql:97-109,362`.
- Risk: any signed-in user, children included since it isn't limited to parents, can call it directly and skip the 10-per-hour limit. Codes are 8 characters from a 32-letter alphabet (about 40 bits), stored as unsalted SHA-256, so brute-forcing one is impractical at PostgREST speeds. A hit would only reveal a nickname and invitation id, letting an attacker take over or block an invitation.
- Fix: revoke from `authenticated` and run the lookup through the admin client after `assertRole("parent")`. `findInvitation` already enforces the limit.

**L2. `getClientIp` trusts the first `x-forwarded-for` hop** (known item)
- Where: `/home/ezio/Desktop/Work/8x/Jarso/src/features/family/server/client-ip.ts:10-11`.
- On Vercel this is fine, because Vercel overwrites the header. If the app is ever put behind Cloudflare or another proxy, or self-hosted, the per-IP limits disappear. Every request without the header also shares one `"unknown"` bucket.
- Fix: prefer `x-vercel-forwarded-for` or `x-real-ip` (set by the platform). Document that this code depends on Vercel.

**L3. The sign-in fields have no maximum length**
- Where: `/home/ezio/Desktop/Work/8x/Jarso/src/features/family/schemas.ts:45-49`.
- `familyCode`, `nickname` and `pin` only check a minimum. Because `familyCode` goes into a rate-limit key, an input of several KB exceeds Postgres's btree row limit and returns an INTERNAL error; it also bloats the counters table. Large PINs are also sent to bcrypt for no reason.
- Fix: cap them at `familyCode.max(12)`, `nickname.max(20)`, and `pin.regex(/^\d{4,6}$/)` (or `max(6)`).

**L4. Children can write a real name into their own profile**
- Where: `/home/ezio/Desktop/Work/8x/Jarso/supabase/migrations/20261028181734_family_core.sql:36-37`.
- `grant update (full_name, avatar_url)` applies to children too. A child can set a real name through PostgREST, and the family-visibility policy then shows it to the rest of the family. This goes against data minimisation.
- Fix: add `role = 'parent'` (or `not exists child membership`) to the profiles update policy's check, or leave child `full_name` for the parent to manage.

**L5. Whoever holds an invitation code gets guardian rights**
- Where: the `acceptInvitation` function at `/home/ezio/Desktop/Work/8x/Jarso/src/features/family/server/service.ts:160-176`.
- Acceptance isn't tied to the stored `parent_email`, so whoever holds the code (for example, someone who saw the child's screen or got a forwarded screenshot) is recorded as the consenting guardian. The invitation is then used up and can't be accepted again.
- Fix: on `/invite`, show the masked address the invitation was sent to (`p***@domain`) so the person accepting can see a mismatch. Optionally, require the accepting parent's verified email to match when the email path was used.

**L6. The invite token travels through redirect URLs**

- Fix (optional): exchange the token for a short-lived httpOnly cookie on the first visit to `/invite`, and remove it from the URL.
