#### Important (fix before merge)

1. **A parent's PIN reset does not end the child's existing sessions, and a child session can set itself a password that survives the reset.**
   - **Where:** `src/features/family/server/service.ts:200-203`; `set_child_pin` at `supabase/migrations/20261028182920_invitations.sql:230-270`; `supabase/config.toml:229` (`secure_password_change = false`).
   - **What happens:** `set_child_pin` only rewrites the bcrypt hash. Anyone holding a child session (an `@supabase/ssr` cookie that JS can read) can call GoTrue `PUT /auth/v1/user {password}` with no reauthentication. After that they can sign in with `<uuid>@child.jarso.invalid` plus that password, directly against GoTrue or via `/login`. That route bypasses the PIN, the lockout and the rate limits.
   - **Why it matters:** the sheet copy promises "The old PIN stops working straight away", and a parent would reasonably expect a reset to lock out whoever learned the PIN. Today it doesn't.
   - **Fix:** in `setChildPin`, after the RPC succeeds:
     - set a new random password with `admin.auth.admin.updateUserById(childId, { password: generateToken() })`;
     - revoke the child's sessions, either by deleting from `auth.sessions` for the child in a security-definer function or via admin signOut.
     
     Also consider blocking password sign-in for the child domain with a GoTrue password-verification hook.

2. **Rule 9 (Zod on every external input) is not met, and some inputs have no length limit.**
   - `src/app/(app)/invite/page.tsx:16-17,29-30` reads `token` and `code` from searchParams with no schema.
   - `childSignInSchema` (`src/features/family/schemas.ts:45-49`) has no `.max` on `familyCode`, `nickname` or `pin`. The client caps them at 16/20/6, but the server does not.
   - `acceptInvitationSchema.invite` (`schemas.ts:39`) is also unbounded.
   - **Why it matters:** the raw `familyCode` becomes the rate-limit key `pin:family:<code>`, stored in the `usage_counters` primary key. A key of a few KB exceeds the btree row limit, which surfaces as INTERNAL, and every request with a distinct code adds a row. This was deferred in Task 8, but it is a hard-rule violation.
   - **Fix:** add a small Zod schema for the invite searchParams, plus `.max(16)` / `.max(20)` / `.max(6)` on the sign-in fields and `.max(128)` on `invite`.

3. **The login page crashes on `?error=__proto__`.**
   - **Where:** `src/app/(auth)/login/page.tsx:19,31`.
   - **What happens:** `linkErrors[error]` on an object literal returns `Object.prototype`, and `FormError` renders that object, so React throws and the login page fails to render.
   - **Why it matters:** anyone can send a crafted link that breaks login. This was deferred in Task 10ab, but it is a one-line fix.
   - **Fix:** use `Object.hasOwn(linkErrors, error)` or a `Map`. Do the same in `src/lib/db-error.ts:13`.

4. **PIN fields use `autoComplete="new-password"`.**
   - **Where:** `add-child-form.tsx:33`, `accept-invitation-form.tsx:43`, `set-pin-form.tsx:61`.
   - **What happens:** on the parent's device the browser offers to save the child's PIN as a site password (with the nickname as username) and may offer a generated "strong password" in a 4–6 digit field.
   - **Fix:** `autoComplete="off"`, as already done in `child-sign-in-form.tsx`. This was deferred in Task 7.

5. **Input borders fail WCAG 1.4.11, which design.md §11 requires.**
   - **Where:** `--input: #E6E2DA` (`src/app/globals.css:152`) on white cards is about 1.3:1. Non-text contrast needs 3:1, and this affects every form in the slice.
   - **Precedent:** Task 6a's ruling on `--destructive` already established that §11 wins.
   - **Fix:** change this one token and update design.md §13. If the designer must decide, record it as an explicit known issue rather than a silent deferral.

14. **Orphan auth users.** If `createChildAuthUser` fails ambiguously (`child-auth.ts:17-32`), an auth user can be left behind. It can't sign in because it has no membership. Defer.
15. **`getClientIp` trusts `x-forwarded-for`** (`client-ip.ts:9-10`). This is fine on Vercel, which overwrites the header, but it should be documented in docs/security.md as triaged. The per-child lockout still limits brute force regardless.
16. **Confirm-link fallback.** If `emailRedirectTo` is not allowlisted, GoTrue falls back to the Site URL, and `nextFromEmailLink` sends the user to `/` instead of `/dashboard`. Treat a bare root as the fallback.
