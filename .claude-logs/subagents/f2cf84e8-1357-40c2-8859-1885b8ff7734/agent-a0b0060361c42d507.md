#### Minor (Nice to Have)

1. **Lockout resets the counter, so brute force runs indefinitely at 5 guesses per 15 minutes** (migration.sql:454-458). On the 5th failure the code sets `failed_attempts = 0`. That sustains 480 guesses per day per child: about 10 days on average to crack a 4-digit PIN, or about 2.6 years for a 6-digit one, while the real child stays locked out the whole time.
   - This matches the global constraint ("5 failures, 15 minutes"), so it is not a spec violation.
   - Recommendation for the controller, spec level: add escalating lockout (for example, double `locked_until` on each consecutive lock and reset only on success or `set_child_pin`), and/or notify the parent on lock. At minimum, make sure the service layer rate-limits per IP and per family code with `hit_rate_limit` before calling `verify_child_pin`.

2. **Lockout works as a nickname-existence oracle and a targeted lockout tool** (:440-443, report concern 5). Someone holding a family code can send 5 wrong PINs for a guessed nickname. If the next response is `locked`, the nickname exists. The same move locks out a real child.
   - This is inherent to per-account lockout. It is listed so the controller consciously accepts it and relies on the per-IP rate limit.

3. **Child rows can have a NULL `nickname_key`, which would bypass the uniqueness index** (:212-219). The check only forces `nickname_key` to be null for non-child rows. NULLs are distinct in a unique index, so any future child insert path (for example Task 4) that forgets `nickname_key` produces rows that dodge uniqueness and can never sign in.
   - Fix: `check ((role = 'child') = (nickname_key is not null))`.

4. **`register_child` will claim any orphan child-role profile whose UUID the caller supplies** (:316-319). Today the only child-role profiles without a membership are the transient ones the server creates just before calling this function, and UUIDs are unguessable, so the risk is low.
   - Task 4 should bind the child id to the invitation rather than trusting a caller-supplied `p_child_id`.

5. **A stale credentials row surfaces as a raw `23505`** (:339-340). The credentials insert sits outside the `unique_violation` handler. If a `child_credentials` row already exists for a child with no membership (only possible after manual deletion of the membership), the raw unique violation is returned instead of `JA409`.
   - Fix: use `on conflict (profile_id) do update`, as `set_child_pin` does, or move the insert inside the handler block.

6. **One error message covers two causes** (:334). "Nickname already used in this family" is also raised for a concurrent duplicate registration of the same child. The code (`JA409`) is right; only the message misleads.
