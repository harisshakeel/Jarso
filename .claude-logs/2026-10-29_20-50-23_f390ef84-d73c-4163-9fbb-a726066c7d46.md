I don't recommend moving these checks into the proxy (Next 16's name for middleware). What you have now is the best-practice pattern, and the fix keeps it. Here is the reasoning, mostly from Next 16's own guide in `node_modules/next/dist/docs/01-app/02-guides/authentication.md`.

**What the Next docs say**
- **The proxy is for optimistic checks only.** It runs on every request, including link prefetches, so the guide says it should "only read the session from the cookie… and avoid database checks."
- **The proxy isn't the main defense.** The guide: "it should not be your only line of defense… The majority of security checks should be performed as close as possible to your data source", meaning a Data Access Layer (DAL).
- **Layouts aren't a safe place either.** A layout doesn't re-render on navigation and doesn't stop nested segments or Server Actions from running.

**Why it can't work for Jarso**
1. **Our checks need the database.** "Is this user an approved parent of child X?" is a database lookup. In the proxy, that lookup would run on every request and prefetch.
2. **The proxy can't tell Server Actions apart.** An action is a POST to the page's URL with an action ID in a header. Path matching can't express "`confirmHandover` needs a parent of this child", so each action has to check inside itself.
3. **Middleware has been bypassed before.** In March 2025, CVE-2025-29927 let anyone skip Next middleware entirely with a single request header (`x-middleware-subrequest`). Apps that relied on middleware for auth were fully open. Checks next to the data are what kept other apps safe.
4. **Project rule.** CLAUDE.md rule 5 and `docs/auth.md` ("Proxy is not security") already settle on: optimistic proxy, then DAL, then RLS.

**How Jarso's layers line up with that**

| Layer | Job | Jarso |
|---|---|---|
| Proxy | Refresh the session, optimistic redirects (cookie only) | [proxy.ts](src/proxy.ts) |
| DAL | Real authorisation, close to the data, cached per request | [dal.ts](src/features/family/server/dal.ts), called by every service |
| Database | Last line of defense | RLS plus security-definer functions |

The guards in the services aren't scattered assertions; they're the DAL entry points the guide recommends. The bug wasn't caused by where the checks live. A read reused the action guard, which also checks profile completion. The fix splits that into two DAL guards, `assertParentCanRead` for reads and `assertParentOf` for actions.

**Where the proxy could help: the profile-completion screen.** This is optional:
- A trigger would add a `profile_complete` flag to the user's `app_metadata` (like `jarso_role`).
- The proxy would redirect incomplete parents from `/parent/**` to a dedicated completion page, so data pages never render for them.
- The DAL check on actions stays as the secure check.

The costs: it changes ADR 0008 from a dialog to a page. The flag is also only as fresh as the session token, so the completion action would have to refresh the session.

I'd ship the current fix as is. The proxy redirect is worth doing only if you'd rather have a completion page than the dialog. Do you want it?

Nothing is broken; this is how the app is designed to work. Scheduled money only reaches the jars after a parent confirms they've actually given it.

The rule in [docs/domain.md:7](docs/domain.md#L7):

> "allowance … count only once a parent has confirmed the handover. Due allowances … never appear in a balance."

Jarso records and teaches; it never holds or moves real money. The app can't know whether you actually gave the ₹200 in cash, so it doesn't count it until you say so. REQUIREMENTS FR01 and invariant 3 say the same, and gifts follow the same rule.

What happened for Child1:
1. On 29 Oct the scheduler created the allowance occurrence (₹200) with status `due`. That's the "Due" badge.
2. The ₹1,000 gift dated 29 Oct is also `due`.
3. No handover has been confirmed yet, so there are no ledger rows and both jars show ₹0. The hosted query earlier also showed 0 ledger entries.

To credit them, tap a row under **Due now** to open the handover screen. Enter how much went to the child as cash (Spend) and how much you keep as savings (Save), then confirm. The jars update immediately and the entry shows in History. If an allowance wasn't actually given, use **Mark not given** instead.

If you'd rather allowances credit automatically, that's a product change, not a bug fix: it would go against FR01 and invariant 3 in the requirements. Tell me if you want to pursue it.

**Research:** design-system guidance on tabs agrees on a few points:
- Tabs suit 3–6 distinct categories that people don't need to compare side by side.
- The tab row goes above the panel, not to the side or bottom.
- Settings pages are a standard use case (Account / Notifications / Privacy is the textbook example).

Jarso's settings fit this well: the family, the children and your own account are separate concerns. `docs/design.md` already lists `tabs` as a primitive to add next.
