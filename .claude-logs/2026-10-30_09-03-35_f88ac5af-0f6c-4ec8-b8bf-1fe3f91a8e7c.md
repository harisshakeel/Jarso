Both research tracks are back. Here's what matters most.

**What prior art says**
- Money apps don't move money offline. They save what the user meant to do, and the server makes the final decision when it reconnects. This matches Jarso's ledger design.
- When an offline action is sent and refused, good apps keep it on screen as "Couldn't send", with a plain reason and the choices to edit, retry or remove. It never quietly disappears, and money is never quietly taken.
- iPhone Safari can't send things in the background. Queued items can only go when the app is open, comes back into view, or the connection returns. For a lot of 11–14-year-olds, that means "next time they open Jarso".

**What the codebase already has, and what's missing**
- **Next 16 offline mode** (`useOffline`) keeps failed page loads and actions waiting and resends them when the connection returns. It only holds them in memory, though, so a reload or a closed tab loses them. A durable on-device queue would have to be built on top.
- **Retry safety:** purchases, handovers, "not given" and mission progress already survive a resend without creating duplicates. Two actions don't:
  - **`create_gift`:** a double tap creates two gifts.
  - **Money guide question:** a resend asks Claude again and records a duplicate turn.
- **Stale sessions:**
  - **Concurrent refreshes:** a tab left idle and then reopened on a slow network can fire several token refreshes that arrive more than 10 seconds apart. Supabase treats that as token reuse and signs the user out.
  - **Removed users:** a removed user keeps a valid sign-in for up to an hour. The database still blocks them.
  - **Sign-out:** it ignores failures, so on a bad network it can fail and leave the user signed in.
- **Work that can hang:** a money guide question can run for about 2 minutes, with no overall time limit and no stop when the user leaves. Supabase calls have no timeout at all, which is your 45-second hang.
- **No browser-side leaks** today: the in-browser Supabase client isn't used anywhere.

**My guess for your earlier question:** a child's purchase that's refused after waiting stays in their diary as "Needs a look". It shows a kind reason, something like "Your Spend jar only has ₹50 left", plus three buttons: change it, ask a parent, or remove it.

Report: what to do when a queued offline write is rejected later

**1. Prior art and UX patterns**
- **WhatsApp**: a message moves through clock (queued), one tick (sent), two ticks (delivered). If it fails, it shows a red "!" and "Message not sent. Tap to retry." The failed item stays in place with one recovery action. https://www.facebook.com/fb-answers/whatsapp-red-exclamation-mark-message-not-sent-tap-to-retry/
- **Gmail**: the Outbox labels unsent mail "Queued" and sends it when the connection returns. The item stays visible until it is sent. https://mailmeteor.com/blog/gmail-queued , https://support.google.com/mail/answer/1306849
- **Linear sync engine** (reverse-engineered, not official): writes are local "transactions" kept with the old values. If the server rejects one (conflict or permissions), the client rolls the change back, and the UI may flicker. Persisted transactions are sent when the app comes back online. https://github.com/wzhudev/reverse-linear-sync-engine
- **Electric and Jazz sync docs**: both say that if the server rejects an offline write, the app must revert local state and tell the user.
