**Verdict: request changes.** Known items 1 and 2 are still Blocking. My read found no new Blocking issues: exactly-once, cross-family authz and gift secrecy all hold. I found one high-priority Should fix.

**Pre-review scan:** clean. The only lines over 500 characters are prose in `.md` files and the secret-pattern regex in `scripts/check-secrets.sh`. No eval, child_process or similar patterns.

**Change to known item 1 (ADR 0007).** Changing the `child_id` FKs and the `remove_child` return value will not be enough. `confirm_handover` checks `is_parent_of` at `20261029130004_handover.sql:18` and only takes the ledger lock later, at `:61`. A `remove_child` that commits in between can check "no ledger rows" and return true. The handover then writes rows, the app deletes the identity, and those rows are lost. The fix needs two parts:
- `remove_child` takes the child's ledger advisory lock (after its `family_members` row lock) before counting rows.
- Both handover functions re-check `is_parent_of` after taking that lock.

This keeps the documented lock order, because handovers never lock `family_members`.

**Should fix**

1. **Not given or cancelled is reported as success.** `20261029130004_handover.sql:44-46` returns `already_confirmed` for a `closed` occurrence, and `20261029130005_parent_gifts.sql:255-257` does the same for a `cancelled` gift. `service.ts:244` shows that result as success.
   - Scenario: parent A marks Tuesday's allowance not given, or cancels a gift. Parent B, on a stale screen, hands over cash and taps confirm. B sees a success message, but no ledger rows exist, so the child's jars are short and no one is told.
   - The tests assert this behaviour: `handover.test.sql:83`, `parent_gifts.test.sql:135`, `handover-race.spec.ts:178`.
   - Fix: return distinct results (`already_closed` / `cancelled`) and show them in the UI.

2. **Spec D11 (injectable `now`) is not met in the database.** Spec line 31 says every time-based function takes an injectable `now`. Only `family_today` and `generate_due_occurrences` do. The others read `now()` directly:
   - `20261029130002_allowance_schedules.sql:285,345,406,454`
   - `20261029130005_parent_gifts.sql:123,178,259,351`

   Slice 6's demo clock would then need nine function signatures dropped and recreated. Either add the parameter now or amend the spec.

**Nits**

- **Manual resume after an expired dated pause** (`20261029130002_allowance_schedules.sql:456-460`) skips every period before today, not just those up to `paused_through`. If cron has lagged by more than a day, periods after the pause end are lost. `allowance_next_due_on` (`:235-241`) shows a stale past date in the same window.
- **`change_allowance` while paused** (`20261029130002_allowance_schedules.sql:354`) accepts a `p_next_on` on or before `paused_through`. Auto-resume (`20261029130003_allowance_generation.sql:54`) then skips that date silently. Reject it with 22023.
