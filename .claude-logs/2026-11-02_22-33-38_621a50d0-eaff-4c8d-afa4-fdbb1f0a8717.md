## 1. Is the threat real, and are there other paths?

**The threat is real.**
- GoTrue is directly reachable with the publishable key. `signInSchema` (`packages/core/src/auth/schemas.ts:13`) only guards `/login`.
- `secure_password_change = true` (`supabase/config.toml:229`, `:451`) only asks for a reauthentication nonce when the session is older than about 24 h. A freshly minted child session can still call `updateUser({ password })` and then use `grant_type=password`. This avoids the PIN rate limits and lockout (`service.ts:270-292`). The 24 h figure comes from GoTrue's source, not from this repo; confirm it locally.
- What changes if the rotation simply stops: today a self-set password survives until the child's next PIN sign-in (`service.ts:296`). It would then survive until a PIN reset, which could be never.
- The realistic danger is not the child but someone who briefly holds the child's session, for example on a shared device. They can set a password and keep silent, PIN-free access.

**Existing hole: `removeChild` with a kept identity** (`service.ts:331-341`). When the child has money history, the identity is kept and only sessions are revoked. The password is not rotated, so a password the child set themselves keeps working after removal. The trigger fixes this too.

**The other paths you listed are closed by current config:**
- **Magic link, OTP, recovery or `reauthenticate` to the `.invalid` address:** the email can't be delivered, so nobody receives the link. Only the admin `generateLink` (server-side, `child-auth.ts:82-92`) gets a usable hash.
- **Email change with `updateUser({ email })`:** `double_confirm_changes = true` (`config.toml:224`, `:449`) needs confirmation on the old, undeliverable address, so the change can't complete. Keep this setting on and treat it as part of the child security model in `docs/auth.md`.
- **Phone, SMS sign-in, manual identity linking and anonymous sign-in:** disabled or not configured (`config.toml:177-181`, `:267-269`).
- **TOTP enrolment** (allowed on production, `config.toml:455-457`): it only raises the session's assurance level and can't be used to sign in, so it isn't a bypass.

**Side effects to keep in mind:**
- An admin `updateUserById({ password })` ends all of the user's sessions. This is why sign-in on one device signs the other out, so your diagnosis is right. It also means the rotation in `setChildPin` duplicates `revoke_user_sessions` (`service.ts:317-318`).
- A user's own `updateUser({ password })` ends all of their other sessions. A child who sets a password themselves would sign out their other device. That only affects the child and is acceptable.
- Both behaviours are from GoTrue's source, not this repo.

## 2. The options

**(a) Password Verification Attempt hook**
- It does close the gap, because it rejects the password grant for child users.
- Pitfalls:
  - My understanding is that this hook is Team/Enterprise only; the project currently looks like free tier (`docs/auth.md:70`).
  - Its payload has `user_id` and `valid` but no app metadata, so it must look up `auth.users` as `supabase_auth_admin`, which needs grants.
  - It doesn't stop `updateUser` itself, and a hook outage blocks every password sign-in, parents included.
- Fine as defence in depth if the plan allows it. Not needed.

**(b) Trigger on `auth.users`**
- Triggers on `auth.users` are allowed. The repo already uses them (`20261029010105_child_role_from_app_metadata.sql:29-36`, and `create_profiles.sql:61`), and the `postgres` owner has DML on `auth` tables (`revoke_user_sessions` deletes from `auth.sessions`, `harden_onboarding.sql:26`).
- **You can't detect `service_role` inside the trigger.** GoTrue writes to the database as `supabase_auth_admin` for both the user's `updateUser` and the admin `updateUserById`. PostgREST and its JWT settings aren't involved, so `current_user`, `session_user` and `request.jwt.claims` look the same in both cases. A trigger that exempts "service_role" would either exempt nothing or exempt everything.
- **You don't need to tell them apart.** Every legitimate password change for a child is already "set to random". So the trigger can replace any child password change with a fresh random bcrypt hash: `extensions.crypt(gen_random_uuid()::text || gen_random_uuid()::text, extensions.gen_salt('bf'))`. pgcrypto is already used this way (`invitations.sql:199`). The admin rotation on PIN reset is then simply randomised again, which is harmless. Better still, remove it.
- **Use BEFORE UPDATE that sets `NEW.encrypted_password`, not AFTER UPDATE.** AFTER UPDATE needs a second UPDATE on `auth.users`, which fires the trigger again and doubles the writes.
- **Don't raise an error.** A RAISE makes GoTrue return a 500 for the child and would also break any admin password update. A silent replacement gives an ordinary "Invalid login credentials" later.
- **Use a random bcrypt hash, not NULL, an empty string or `OLD`.**
  - A random bcrypt keeps GoTrue on its normal comparison path.
  - Keeping `OLD` would leave a password a child already set before the migration working.
- **Base the condition on `NEW.raw_app_meta_data ->> 'jarso_role' = 'child'` only.** Users can't write app metadata. Never use user metadata.
- **Guard with `WHEN (new.encrypted_password is distinct from old.encrypted_password)`.** Some GoTrue updates write the whole row, and the guard avoids a bcrypt run for each of them.
- **Creating a user still works.** `createUser` sets the random password in the INSERT and writes app metadata in a later UPDATE of that column only (`create_profiles.sql:61`, `child_role_from_app_metadata.sql:3-7`), so the trigger isn't involved and the initial password stays random.
- **The migration must also re-randomise existing child passwords once,** because a child may already have set one.
- **Function style:** follow the existing trigger function: `security definer`, `set search_path = ''`, `revoke execute … from public, anon, authenticated` (`child_role_from_app_metadata.sql:9-27`).

**(c) Other ideas**
- **Blocking the child domain in the app's schemas:** doesn't close it. GoTrue is reachable directly.
- **A BEFORE trigger that raises:** worse than replacing the hash, for the 500 reason above.
- **GoTrue config:** nothing in `config.toml` blocks password sign-in per user or per domain. `secure_password_change` is already on and doesn't stop a fresh session. Recent GoTrue may have a "require current password on update" setting; I couldn't confirm it. If it exists it would close the `updateUser` path, since the child doesn't know the random current password. Check the dashboard; it's a bonus, not the fix.
- **Custom Access Token hook (all plans):** it could refuse to issue tokens when the claims' `amr` contains `password` for a child. That covers refreshes too. But it runs on every token for every user, so a bug locks everyone out. I'd only use it as a later extra layer.
