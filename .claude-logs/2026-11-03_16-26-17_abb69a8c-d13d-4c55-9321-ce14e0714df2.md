## Mobile wave 2 recon: child guide, outbox and e2e tests

**Main finding.** `assertRequestUser` checks a bearer token, but nothing builds a Supabase client from that token for each request. Every service behind `/api/v1/guide/turns` and `/api/v1/outbox` gets its user and client from cookies: `assertRole` → `assertUser` → `getCurrentUser`, and `createClient()` reads `cookies()`. Swapping `assertUser` for `assertRequestUser` in those routes is therefore not enough. Wave 2 has to pass a bearer client through the services, or set up a request-scoped client/user that `assertRole` and `createClient` read.

## 1. Scope leaking across requests: Fine. One fragile spot is worth a test.
- **ALS:** `AsyncLocalStorage.run` scopes to the async continuation of `fn`. Concurrent requests cannot see each other's store. The only leak would be a module-level value set inside a scope. I found none in the outbox or guide chain:
  - `config.ts:23 let provider` is the Anthropic or fake provider. It holds no user state.
  - `guideBreaker` is global on purpose.
  - The `CACHE_HEADERS` const in `lib/supabase/proxy.ts` is a constant.
- **Guide streaming:** `stream.ts:21` does the work in `start()`, which runs synchronously inside the `ReadableStream` constructor while still inside the scope. So `runGuideTurn` and its tools keep the scope after the handler has returned the `Response`. The tools call `getSchedule`, `getGoalView` and so on, which call `createClient` and `assert*`. If anyone moves that work to `pull()`, it runs in the consumer's context. `createClient()` would then silently fall back to cookies, which means anon or the wrong identity. Add a test (see 5).
- **`after()`:** Next wraps callbacks with `bindSnapshot` (`next/dist/server/after/after-context.js:103`), so they inherit the request's ALS context, including the bearer scope. That is correct. Today `dispatchPush` / `pushAfterNotices` use only the admin client anyway.
- **React `cache()`:** Memoisation is per request at most; in route handlers it may be a pass-through. Either way it cannot cross requests. `getCurrentUser` takes no arguments, so it is only safe because the whole handler runs inside the scope. Keep the `currentScope()` check inside the cached function, as Step 4 says. Never call `getCurrentUser` / `getMembership` in `withApi` before entering the scope. `getRole(userId)` and `parentOfChild(childId)` take ids as keys, so they are fine.
- **Admin client:** In `service.ts` (`storedTurn`, `recordTurn`, `hitRateLimit`, `startConversation`, `usageSince`) and in `tools.ts:370` (`remember`), the admin client is always keyed by `childId` / `userId` from `resolveAsker` → `assertRole`. That comes from the scope user, not from the body. No IDOR.

## 2. Token verification: Should fix
- **What `getClaims(token)` does:** It checks `exp` locally. With asymmetric signing keys it checks the signature against the project's JWKS locally. With HS256, a missing `kid`, or no WebCrypto, it falls back to `GET /auth/v1/user`. Signature and expiry are covered either way.
- **What it does not do:** It does not check `role`, `aud` or `is_anonymous`. On the local path it does not check whether the session was revoked, so a signed-out or deleted child's token stays valid until `exp`. `jwt_expiry = 3600` in `supabase/config.toml`. The cookie path has the same limit, so this is parity, not new risk. Do not add a `/user` round trip.
- **Should fix: validate claims in `verifyBearer`.** Require all of the following, otherwise return `UNAUTHORIZED`:
  - `typeof sub === "string"` and it is a UUID
  - `role === "authenticated"`
  - `aud` is or contains `"authenticated"`
  - `is_anonymous !== true` (anonymous sign-ins are off in config, but check anyway)

  Why: the scoped client forwards the raw token to PostgREST. This check keeps any non-user JWT (a legacy `anon` or `service_role` token) from ever becoming the scope client, and keeps `id: undefined` from reaching admin-client queries keyed by user id. Today `request-user.ts:33` returns `data.claims.sub` unchecked.
- **Should fix: keep the token out of `user`.** `verifyBearer` returns `SessionUser & { token }`. Store `{ id, email }` only as `scope.user`, and have `assertRequestUser` return `{ id, email }` too. Otherwise any future `json(user)` or `logger.*({ user })` leaks the access token into responses or logs, and logs are public. Also never put the header or the token in an `AppError` `cause`.
- **Fine:** A token that expires mid-request (a guide turn can run up to 60 s) makes later PostgREST calls fail with JWT expired. That is a reliability issue, not security. The phone should refresh when a token is close to expiry.

## 3. CSRF: Fine
- Browsers never attach `Authorization` on their own. A cross-site page cannot set it without a CORS preflight, and no CORS headers are configured in `next.config.ts` or `proxy.ts`. So a bearer request is not CSRF-able.
- `assertSameOrigin` still runs first. Native Expo `fetch` sends no `Origin`, so it passes. Expo **web** dev (localhost:8081) would get FORBIDDEN on POST. That is expected; just document it.
- **Bearer plus cookies:** no need to reject. The bearer wins and cookies are never read on that path. An attacker cannot make a victim's browser send a bearer token, and sending your own token gains nothing. Rejecting the combination would only break a signed-in web user debugging from the same browser.
- Make sure `runInBearerScope` (and so `verifyBearer`) runs inside `withApi`'s `try`, so a 401 or 503 becomes the JSON error and not an unhandled 500.
- **Fine:** `proxy.ts` also runs on `/api/v1`. A bearer request without cookies gets `claims = null`, and `/api/v1` is not a protected prefix, so it passes through.

## 4. Cookie writes or `supabase.auth.*` in the chain: Fine
- `rg` over `apps/web/src` finds `cookies()` only in `lib/supabase/server.ts:13`. That call is bypassed when a scope exists. It finds `auth.getClaims()` only in `session.ts:20` (short-circuited before it), `request-user.ts` and `proxy.ts`. It finds `auth.signOut()` only in `features/auth/server/actions.ts:68`, a server action that is not on a bearer route. No service in the outbox or guide chain sets cookies or calls session methods.
- **Optional hardening:** build the scoped client with `accessToken: async () => token` instead of `global.headers.Authorization`. supabase-js then throws on any `supabase.auth.*` access, so a future `getClaims()`, `getUser()` or `signOut()` on the bearer client fails loudly instead of quietly returning null. It also stops a later `setSession` from changing the token. `getCurrentUser` must short-circuit before touching `.auth`, which the design already does.
- `headers()` in `notifications/server/actions.ts:23` and `family/server/client-ip.ts:9` only reads, and neither is on these routes.

## 5. Tests to add (beyond the five listed)
1. **Claims checks:** `role !== "authenticated"`, missing or non-UUID `sub`, `aud` mismatch, or `is_anonymous: true` → 401. The `next/headers` `cookies` mock is never called.
2. **Bad headers:** `Authorization: ""`, `Basic x`, `Bearer` with no token, and `Bearer a b` → 401 with no cookie read. `headers.get` returns `""`, not `null`.
3. **Bearer plus a cookie user:** bearer present and the cookie mock returning a different user → the bearer user wins and `cookies()` is never called.
