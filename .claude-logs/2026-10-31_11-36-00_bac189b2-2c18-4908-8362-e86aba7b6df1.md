I've rewritten the design with the Stripe research and your ask that a second provider be easy to add. It's in `docs/superpowers/specs/2026-10-31-stripe-card-handover-design.md`, not committed yet.

**How a second provider stays easy:**
- All the money logic talks to one `PaymentProvider` interface: start a checkout, save a card, charge a saved card, remove a card, check and translate incoming confirmations. Stripe sits behind it as the first adapter.
- Every table is generic (`payments`, `payment_customers`, `payment_setups`, `payment_webhook_events`) and carries a `provider` column. Stripe-specific values are stored only as opaque references.
- Each provider gets its own confirmation URL, `/api/v1/payments/webhooks/[provider]`. A setting, `PAYMENTS_PROVIDER` (`none` | `stripe` | `fake`), chooses the active one; `none` means payments are off.
- Adding a provider means a new folder, one line to register it, its env vars, and passing a shared test suite that every adapter must pass. No migration, no change to the handover logic or screens. That checklist is §8 of the design.
- A `fake` provider stands in for Stripe in tests and in local dev.

**What the research changed (§7):**
- Stripe's server library (`stripe` 23.x) is pinned to a fixed API version.
- Confirmations from Stripe can arrive out of order or more than once. Each payment's status only ever moves forward, which handles that. Anything flagged as live (real money) is rejected.
- Stripe forgets a duplicate-request key after about 24h. So each charge attempt is a new payment record, never a reused key.
- When a parent saves a card, they see a short statement of what Jarso will charge and when. UK/EU cards require this before charging without the parent present.
- It also lists minimum charge amounts per currency, test cards for the demo, and how to receive Stripe's confirmations on a local machine.

**Calls I made. Please check these while reading:**
1. **Card payments.**
   - A card always pays the full amount; the cash option still allows giving less.
   - With auto charge on, the split is the last one the parent used, or all to Spend if there isn't one yet.
2. **Auto charge.**
   - It only covers items that fall due after the toggle is switched on, so it never back-charges overdue allowances.
   - It makes one attempt per item, and saving a new card doesn't retry old failures. A failed charge leaves the item due and sends the parent an inbox notice.
3. **Races between cash and card.**
   - If cash is handed over first, a later card payment is recorded without touching the jars, and the parent is told to refund it from Stripe's dashboard.
   - While a card payment is in progress, the parent can't edit or cancel that gift, or mark that allowance as not given.
4. **When auto charge runs.** Vercel's free plan only runs scheduled jobs once a day. So the hourly database scheduler calls the charge job at :09, and a daily Vercel run acts as a backup.
5. **"Paid by card" for the child.** It comes from one new column on money records, `ledger_entries.method`. That's the only change to how money is stored.
6. **Currencies.** Currencies without decimals (yen, won and similar) are turned off for card payments for now. Payments below Stripe's minimum show the button disabled with "Too small to pay by card".

Approve it or tell me what to change. Once it's approved, I'll write the implementation plan.

I've written the plan: `docs/superpowers/plans/2026-10-31-card-handover-payments.md`. Nothing is committed yet. On the branch so far: the plan, the spec, the new env vars in `src/config/env.server.ts`, and `stripe` 23.1.0 added to `package.json`. No tests have run, because no payment code exists yet.

It has 8 tasks, each with its own tests and commit:
1. **Provider layer in `src/lib/payments`**: the shared interface, provider selection, the Stripe and fake adapters, and one test suite every provider must pass.
2. **Database**: the payment tables, the auto-charge columns, `apply_payment` (posts a card handover exactly once, same locking as cash), and database-level tests.
3. **Starting payments**: Pay by card, saving a card, the auto-charge toggle, removing a card.
4. **Incoming confirmations**: a per-provider URL for each provider's payment confirmations. Payment states only move forward, and duplicate confirmations are ignored.
5. **Auto charge job**: the charge route, hourly scheduling from the database, and a daily Vercel backup.
6. **Screens**: Pay by card on the handover screen, the toggle on allowance and gift forms, the saved-card panel in settings, the failed-charge notice, and "Paid by card" in history.
7. **End-to-end test**: a fake checkout page and a full Playwright run against the fake provider.
8. **Docs**: ADR 0012, deploy, API and security docs, then full verification.

Three choices I made while planning. I've updated the spec to match:
- **One posting function, `apply_payment`,** in place of the spec's separate allowance and gift versions.
- **Overlapping auto-charge runs:** each run claims an item by inserting its payment record. A one-automatic-attempt-per-item rule in the database makes the second run skip, so no row locking is needed.
- **Error codes:** provider failures reuse the existing `UNAVAILABLE` error code. The spec had a new `PAYMENT_PROVIDER` code.

The plan also names five edge cases that the tests must cover. One example: a confirmation from Stripe for a payment this database doesn't know about. Local, preview and production share one Stripe test account, so this will happen, and the app should accept and ignore it rather than error.

How should I build it?
- **Subagent-driven**: a fresh agent builds each task and a fresh reviewer checks it before the next starts. Most thorough, and costs more.
- **Native**: I build every task here, then one reviewer checks the whole branch at the end. Cheaper and faster.

I recommend subagent-driven. Each task depends on exact names and signatures from earlier ones, and a mistake here could post money twice, so a review after every task is worth it.

**1. SDK and API version**
- `stripe` on npm is at **23.1.0**, released 2026-10-29. That release pins API version **`2026-10-28.endive`** (stated in its CHANGELOG and set as `ApiVersion` in the source).
- Pin it explicitly with `new Stripe(key, { apiVersion: '2026-10-28.endive' })` and lock the package major version. Webhook endpoints have their own API version: set it to the same value when creating the endpoint.
- New detail: the save-and-reuse docs now show `customer_account` (an Accounts v2 ID) in examples. The classic `customer` param still exists alongside it, so plain Customers are fine for us.
- Source: https://github.com/stripe/stripe-node/blob/master/CHANGELOG.md

**2. Webhooks in an App Router Route Handler**
- Read the raw body with `const body = await req.text()` and pass it with `req.headers.get('stripe-signature')` to `stripe.webhooks.constructEvent(body, sig, whsec)`.
  - `constructEvent` is synchronous and uses Node crypto. Use `export const runtime = 'nodejs'`.
  - `constructEventAsync` is for Edge/SubtleCrypto runtimes; we don't need it.
  - Default timestamp tolerance is 5 minutes.
  - Stripe: "Any manipulation to the raw body… causes the verification to fail."
- Ordering is **not guaranteed**.
- Retries: live mode retries for up to **3 days** with exponential backoff. Sandbox/test mode retries **3 times over a few hours**.
- Duplicates: store processed `event.id`s. Stripe also notes two separate Event objects can occasionally be sent for the same change, so also dedupe on `data.object.id` plus `event.type`. A unique DB constraint on the business key is the practical guard.
- Return 2xx **quickly, before complex logic**. A single DB transaction is fine; slow work should not block the response.
- Source: https://docs.stripe.com/webhooks

**3. Events to handle**
- **Payment-mode Checkout:** fulfil on `checkout.session.completed` only when `payment_status` is `paid`. Also handle `checkout.session.async_payment_succeeded` / `async_payment_failed`; with cards only, payment is effectively synchronous. Handle `checkout.session.expired` to clean up.
  - `payment_status` values: `paid | unpaid | no_payment_required`.
  - The fulfil function must be safe to run many times, even concurrently. Stripe also recommends fulfilling on the success page, but never only there. https://docs.stripe.com/checkout/fulfillment
- **Setup-mode Checkout:** on `checkout.session.completed`, read `session.setup_intent`, retrieve it (or expand it), and take `setupIntent.payment_method`. `session.customer` is set if you passed `customer`; otherwise attach the PaymentMethod to a Customer yourself. Simplest is to always create the Customer first and pass it. https://docs.stripe.com/payments/checkout/save-and-reuse
- **Off-session charges:** handle `payment_intent.succeeded`, `payment_intent.payment_failed` and `payment_intent.requires_action`. Read `last_payment_error.code` and `decline_code`.
- **Event fields:** events carry `livemode: boolean` (assert it is `false`) and an optional `account` field that is only set for Connect events.

**4. Checkout Session create params**
- `expires_at`: **30 minutes to 24 hours** after creation; default is 24 hours.
- `client_reference_id`: a free-form string for reconciliation. Put our payment row ID here.
- `metadata`: Stripe documents a limit of 50 keys, 40-character keys and 500-character values (from memory; not re-verified this session).
- `payment_intent_data.setup_future_usage: 'off_session'` lets the manual payment also save the card. You need a `customer`, or the PaymentMethod must be attached afterwards. One flow can cover both pay and save.
- `customer_creation: 'always' | 'if_required'` applies to payment and setup mode. Passing an existing `customer` is cleaner.
- `saved_payment_method_options` applies to payment and subscription mode only.
- Idempotency keys: up to 255 characters. Stripe may prune them once they are at least 24 hours old. Reusing a key with different params returns an error.
- Sources: SDK `cjs/resources/Checkout/Sessions.d.ts`; https://docs.stripe.com/api/idempotent_requests

**5. Off-session charges**
- Call `paymentIntents.create({ amount, currency, customer, payment_method, off_session: true, confirm: true }, { idempotencyKey })`. Derive the key from the scheduled-charge row ID.

#### Critical (Must Fix)
1. **The Stripe Checkout `expires_at` is probably under Stripe's 30-minute minimum, so every manual Pay by card on Stripe would fail.** `src/features/payments/server/service.ts:48,226` and `src/lib/payments/stripe/index.ts:77`.
   - `expiresAt = Date.now() + 30 min` is computed before `ensureCustomer` (sometimes a Stripe round trip), `insertPayment` and `listChildren`. The adapter then floors it to seconds.
   - The SDK's own docs (`node_modules/stripe/esm/resources/Checkout/Sessions.d.ts:2251`) say "anywhere from 30 minutes to 24 hours after Checkout Session creation". By the time Stripe creates the session, the window is 30 minutes minus a few hundred to about 1,200 ms.
   - If Stripe enforces this strictly, every manual card payment would return "Card payments aren't available right now". That is the headline flow of the showcase.
   - Tests mock the Stripe client, and the real-Stripe pass was skipped (Ruling 126), so nothing would have caught it.
   - I can't verify this without keys, but the fix is one line: use a buffer (`CHECKOUT_MINUTES = 31`) so the DB and Stripe expiry stay equal. Alternatively, the adapter can clamp to `max(expiresAt, now + 30m + 60s)` and return the real expiry for the service to store. Either fix it, or prove it with one real test-mode call before merge.

#### Important (Should Fix)
2. **Reusing a checkout silently uses the old split, and an abandoned checkout locks the item for 30 minutes.** `service.ts:287-299` (`reuseLive`) and Ruling 60.
   - The likely path: the parent taps Pay by card, presses Back or Cancel on Stripe (`?card=cancelled`), changes the Spend/Save split, and taps Pay by card again. They get the first checkout, and the child's jars get the split the parent just changed away from.
   - The ruling's reason ("the provider can't expire a session") doesn't apply. The split never goes to the provider (Stripe only sees the full amount), so `reuseLive` can simply update `cash_minor`/`saved_minor` on the live manual row (`where status = 'pending'`) before returning the URL. `apply_payment` locks that row, so the update is race-safe.
   - Same root cause: after an abandoned checkout, "Card payment in progress" shows for 30 minutes. During that time `mark_not_given`, `update_gift` and `cancel_gift` return JA409.
   - Cheap fix for that: on the `?card=cancelled` return, or with a small "Cancel card payment" button, cancel the parent's live manual row with `fail_payment(..., 'canceled')`. This is money-safe because `apply_payment` still posts a late success from `canceled`.
3. **Auto charge silently never runs for amounts it can't charge, and those items can fill every batch.** `auto-charge.ts:79` (deferred minor "hourly warning for items below the minimum").
   - Family currencies include JPY (`src/features/family/currency.ts`), and `stripeMinimumChargeMinor("JPY")` is null. Small amounts (for example under GBP 0.30) are also uncharged.
   - In both cases the auto-charge toggle still renders and can be turned on, a card can be saved, and every run returns `skipped`. No auto row is written and the parent never gets a notice: the allowance just doesn't arrive.
   - Because nothing is written, those items come back on every run, oldest first, inside `LIMIT 50`. Enough of them would crowd out newer chargeable items indefinitely.
   - Fix: claim the item anyway by inserting the auto row and then `fail_payment(id, 'failed', 'other')`. That keeps the one-attempt rule, notifies the payer once and frees the batch. Also hide or disable the toggle when `minimumChargeMinor` is null for the family currency.
