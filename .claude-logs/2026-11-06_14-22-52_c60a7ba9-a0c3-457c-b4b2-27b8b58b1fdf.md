# First day on Jarso

## 1. Getting oriented

1. **Read** `REQUIREMENTS.md`, `docs/domain.md`, `docs/architecture.md` and `docs/conventions.md`, in that order. ([CLAUDE.md](CLAUDE.md), "Read before working")
2. **Learn the four workspaces.** `apps/web` is the Next.js 16 app. `apps/mobile` is the Expo app. `packages/core` holds pure domain code: schemas, types, rules and copy. `packages/data` holds the Supabase repositories that the web and the phone share, and each one takes a Supabase client as an argument. ([CLAUDE.md](CLAUDE.md), intro and Hard rule 1)
3. **Copy** `.env.example` to `apps/web/.env.local` before `pnpm build`. The three source docs don't cover local Supabase setup (Docker, `pnpm db:start`), so ask for that or check `docs/database.md`. ([CLAUDE.md](CLAUDE.md), Commands)

## 2. Adding a feature module

4. **Create the core module first** in `packages/core/src/<name>`. Add `"./<name>"` to `exports` in `packages/core/package.json`, and add the module to its layer group in `biome.json`. ([new-feature skill](.claude/skills/new-feature/SKILL.md), step 3)
5. **Create the web module.** Use `features/profiles` as your reference: ([new-feature skill](.claude/skills/new-feature/SKILL.md), step 3)
   ```
   apps/web/src/features/<name>/
   ├── index.ts
   ├── components/
   └── server/{index,actions,service,repository}.ts
   ```
6. **Follow the layering** route → action → service → repository → Supabase. The action calls `assertUser()` and then the service. The service holds the business rules and throws `AppError`. Only the repository names tables and columns. `app/` only routes and composes. ([CLAUDE.md](CLAUDE.md), Hard rules 1, 4, 5; [new-feature skill](.claude/skills/new-feature/SKILL.md), steps 4–6)

## 3. Barrels

7. **Export the client-safe API** from `index.ts`. This is the real profiles barrel: ([docs/conventions.md](docs/conventions.md), "Index barrels")
   ```ts
   export * from "@jarso/core/profiles";
   export * from "./components/profile-card";
   export { updateProfileAction } from "./server/actions";
   ```
8. **Put server-only exports in `server/index.ts`**, starting with `import "server-only";`. A mixed barrel would pull server code into the client bundle. ([docs/conventions.md](docs/conventions.md), barrel rule 1)
9. **Import across modules only through barrels** (`@/features/auth`, `@/lib`). Inside your own module, use relative imports, never your own barrel, because that causes import cycles. ([docs/conventions.md](docs/conventions.md), rules 2–3)
10. **Import these directly, not through a barrel:** `@/lib/supabase/{client,server,admin,proxy,stateless,request-scope}`, `@/lib/payments` and `@/config/env.server`. Keeping them separate stops the wrong client from landing in the wrong runtime. ([docs/conventions.md](docs/conventions.md), rule 4)

## 4. Validating input with Zod

11. **Define schemas in `packages/core/src/<name>/schemas.ts`.** Name them `<thing>Schema` and infer `<Thing>Input`: ([docs/conventions.md](docs/conventions.md), Naming)
    ```ts
    export const updateProfileSchema = z.object({
      fullName: z.string().trim().min(1, "Name is required").max(100),
    });
    export type UpdateProfileInput = z.infer<typeof updateProfileSchema>;
    ```
12. **Wrap Server Actions in `createAction(schema, handler)`.** It validates `FormData` or an object and returns `{ ok, data }` or `{ ok: false, error }`. ([CLAUDE.md](CLAUDE.md), Hard rule 9)
13. **Use `withApi` + `parseBody(request, schema)` in Route Handlers.** Add one only when something other than our own UI calls it. Details are in `docs/api.md`. ([CLAUDE.md](CLAUDE.md), Hard rule 9)

## 5. Errors and logging

14. **Throw `AppError(code, userSafeMessage, { cause })`** for expected failures (`NOT_FOUND`, `FORBIDDEN`, `CONFLICT`, …). Any other error becomes `INTERNAL`, and its raw message never reaches the user. ([docs/conventions.md](docs/conventions.md), Errors)
15. **Log with `logger` from `@/lib`.** `console.log` is a lint error. Never log tokens, passwords or full user rows. ([docs/conventions.md](docs/conventions.md), Logging)

## 6. Verifying the work

16. **Run `pnpm check`.** It runs Biome lint, typecheck and unit tests across every package through Turbo. It must pass before any commit. ([docs/conventions.md](docs/conventions.md), Tooling; [docs/testing.md](docs/testing.md))
17. **Put tests in the right place:** web tests under `apps/web/tests/` mirroring `src/`, and core tests in `packages/core/tests/<name>/`. Always test schemas and branching service logic. ([docs/testing.md](docs/testing.md), "What to test")
18. **Run `pnpm build` too, and `pnpm test:e2e` if you changed routes or user flows.** E2E needs local Supabase running (`pnpm db:start`). The first time, run `pnpm --filter @jarso/web exec playwright install chromium`. ([verify skill](.claude/skills/verify/SKILL.md); [docs/testing.md](docs/testing.md), "End-to-end against local Supabase")
19. **"Done" means** every step above passed, and you report any step you skipped as skipped. The source docs don't define a PR review process. ([verify skill](.claude/skills/verify/SKILL.md), Report)

## 7. Commits and PRs

20. **Write commits as `type(scope): subject`**: lowercase, imperative, 72 characters or fewer, e.g. `feat(goals): add payments-remaining estimate`. commitlint enforces this locally and in CI. PR titles are checked the same way, because the title becomes the squash-merge commit. ([docs/conventions.md](docs/conventions.md), "Commits & PRs")

## Common first-day mistakes

- Deep-importing another module (`@/features/auth/components/sign-in-form`) instead of using its barrel.
- Reading `process.env` outside `config/env.{client,server}.ts`, or adding a variable without updating `.env.example`.
- Importing `@/features/*/server` or `@/lib/supabase/server` from a `"use client"` file.
- Putting React, Next or `window` in `packages/core` (Biome fails the build).
- Storing money as floats. Use integer minor units only.
